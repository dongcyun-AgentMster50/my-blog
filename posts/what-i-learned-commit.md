블로그를 GitHub에 올리면서 커밋(commit)이라는 말을 계속 마주쳤습니다. 그냥 "저장"이라고 생각하고 넘어갔는데, 실제로 커밋 하나를 열어보고 나서야 제가 완전히 잘못 알고 있었다는 걸 알았습니다.

## 커밋은 "고친 부분"이 아니었다

저는 커밋이 **제가 바꾼 내용**을 담고 있다고 생각했습니다. 파일 하나에서 한 줄을 고쳤으면, 그 한 줄이 커밋에 들어 있을 거라고요.

그래서 커밋 안을 직접 열어봤습니다.

```bash
git cat-file -p HEAD
```

나온 것은 이게 전부였습니다.

```
tree      ce59ddb1233e7c2e284b241412b812a2e73110de
parent    18b358866ab7b673105950b6ae47f89163d23623
author    David Yoon <...> 1787791238 +0900
committer David Yoon <...> 1787791238 +0900

문서의 git 관련 안내 문구 수정
```

제가 고친 한 줄은 어디에도 없었습니다. 대신 **네 개의 정보**가 있었습니다.

## tree — 그 순간의 사진

`tree`를 따라 들어가 봤습니다.

```bash
git cat-file -p HEAD^{tree}
```

```
100644 blob 3cc3002...  CLAUDE.md
100644 blob c6e8d4b...  README.md
100644 blob 0cb41c9...  index.html
040000 tree b30afce...  css
040000 tree ecd3957...  js
040000 tree 1880f34...  posts
...
```

제가 고친 `CLAUDE.md`만 있는 게 아니라 **폴더 전체**가 들어 있었습니다. 손도 안 댄 `index.html`도, `vendor` 폴더도 전부요.

그러니까 커밋은 변경사항이 아니라 **그 순간 프로젝트 전체를 찍은 사진**이었습니다. 커밋 하나만 있으면 그 시점으로 통째로 돌아갈 수 있는 이유가 이것이었습니다.

여기서 당연한 의문이 들었습니다.

> 커밋할 때마다 프로젝트 전체가 복사되면, 파일이 금방 어마어마해지는 거 아닌가?

아니었습니다. 안 바뀐 파일은 **같은 번호를 다시 가리킬 뿐**입니다. 위 목록의 `3cc3002` 같은 번호들이 그것인데, 이번에 고친 `CLAUDE.md`만 새 번호를 받았고 나머지는 이전 커밋과 똑같은 번호를 그대로 씁니다.

사진첩에 같은 사진을 여러 장 인화해 붙이는 게 아니라, 한 장을 여러 페이지에서 함께 가리키는 방식입니다.

## parent — 손을 잡고 있는 줄

`parent`는 바로 앞 커밋을 가리킵니다. 이 한 줄이 역사를 만듭니다.

```
fa1b1a7 ──parent──▶ 18b3588 ──parent──▶ (없음, 최초 커밋)
```

각 커밋이 앞사람 손을 잡고 있고, 그 사슬이 그대로 `git log`에 보이는 목록이 됩니다.

그래서 **변경사항은 저장된 게 아니라 계산되는 것**이었습니다. `git show`를 쳤을 때 초록색과 빨간색 줄이 나오는 건, git이 이 커밋의 사진과 부모의 사진을 그 자리에서 비교해서 보여주는 것이었습니다. 저장해둔 걸 꺼내는 게 아니라요.

## commit이라는 말은 은행에서 왔다

단어 자체가 궁금해서 찾아봤습니다. 프로그래밍이 만든 말이 아니었습니다.

라틴어 **committere**(com- "함께" + mittere "보내다")가 어원이고, "맡기다, 확정하다"라는 뜻입니다. 영어 commit이 "약속하다"인 것도 여기서 나왔습니다.

이 말이 컴퓨터로 넘어온 건 1970년대 **데이터베이스**에서였습니다. 계좌 이체를 생각하면 쉽습니다.

```
A 계좌에서 10만원 빼기    ← 아직 확정 아님
B 계좌에 10만원 넣기      ← 아직 확정 아님
COMMIT                    ← 이제 확정
```

중간에 문제가 생기면 `ROLLBACK`으로 전부 없던 일이 됩니다. 돈이 A에서만 빠지고 B에 안 들어가는 사태를 막는 장치인데, 여기서 **"작업을 모아뒀다가 한 번에 확정한다"** 는 뜻이 자리 잡았습니다.

버전 관리 도구들이 이 말을 그대로 가져왔습니다. RCS(1982) → CVS(1990) → Subversion(2000)을 거치며 굳었고, Git(2005)도 이미 익숙해진 이 단어를 물려받았습니다.

재미있는 건 **어원이 지금도 그대로 살아 있다**는 점입니다.

```bash
git add index.html    # 담아두는 중 — 아직 확정 아님
git commit -m "..."   # 확정
```

`git add`로 담아두는 동안은 아직 아무것도 확정되지 않습니다. 데이터베이스의 그 구조와 정확히 같습니다.

## 언제, 어떻게 커밋할까

배운 것을 정리하면 이렇습니다.

| | 내용 |
| --- | --- |
| 언제 | 한 문장으로 설명되는 일 **하나**가 끝났을 때 |
| 제목 | 무엇을 했는지 한 줄 (50자 안쪽) |
| 본문 | **왜** 그렇게 했는지 |
| 순서 | 동작을 확인한 **다음에** 커밋 |

제목에 "무엇을", 본문에 "왜"를 쓰는 이유가 인상적이었습니다. 무엇을 했는지는 코드를 보면 알 수 있지만, **왜 그랬는지는 코드 어디에도 남지 않기 때문**입니다.

한 커밋에 여러 가지를 담으면 나중에 "이것만 되돌리고 싶다"가 불가능해집니다. 셋이 한 몸이라 하나만 뗄 수 없으니까요.

조심할 것도 하나 배웠습니다.

> `git commit --amend`는 방금 만든 커밋을 고칩니다. 하지만 이미 GitHub에 올린 뒤에는 쓰면 안 됩니다. 커밋을 수정하는 게 아니라 **새것으로 갈아치우는** 것이라, 올라간 기록과 어긋나기 때문입니다.

실제로 제 첫 커밋 메시지에 이상한 문자가 들어갔을 때 이걸로 고쳤습니다. 아직 안 올린 상태였으니 괜찮았습니다.

## 진짜 얻은 것

커밋의 효용이 "기록"인 줄 알았는데, 써보니 아니었습니다.

**겁 없이 실험하게 되는 것**이었습니다. 돌아올 지점이 있으니 과감하게 뜯어고칠 수 있습니다. 그래서 "확실해지면 커밋해야지"가 아니라 **"돌아오고 싶은 지점이면 커밋"** 이 맞다는 걸 알았습니다.

다만 순서는 지켜야 합니다. 동작을 확인한 다음에 커밋 — 고장 난 상태를 기록해두면 돌아갈 이유가 없는 지점이 하나 늘어날 뿐이니까요.
