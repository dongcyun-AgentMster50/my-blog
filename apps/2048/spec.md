# 2048 — 설계 문서 (spec)

4×4 격자에서 방향키(데스크톱) 또는 스와이프(모바일)로 숫자 타일을 한 방향으로 밀어, 같은 숫자끼리 합치며 2048을 만드는 퍼즐 게임이다. 프레임워크·번들러·외부 라이브러리 없이 순수 HTML/CSS/JavaScript로 `/apps/2048/` 폴더 안에서 자체 완결되며, 빌드 단계 없이 브라우저가 파일을 그대로 읽어 동작한다. 점수판(현재 점수·최고 점수)과 1단계 실행 취소, 다시 시작 버튼을 갖추고, 블로그 메인 페이지에 iframe으로 임베드될 것을 전제로 고정 픽셀이 아닌 컨테이너 반응형 크기 정책을 따른다.

---

## 1. 파일 구조

```
apps/2048/
├── index.html    마크업 + 메타 태그. 스타일·스크립트 링크만 하고 로직은 담지 않는다.
├── style.css     레이아웃, 타일 색상 팔레트, 반응형/다크 모드, 애니메이션
├── game.js       게임 상태·규칙·입력 처리·렌더링 (단일 클래식 스크립트)
├── spec.md       이 문서
└── review.md     Review 단계에서 생성 (Plan/Build 단계에서는 만들지 않는다)
```

### 왜 하나로 합치지 않고 3개로 나누는가

- **프로젝트 관례와 일치한다.** 블로그 본체가 이미 `css/`와 `js/`를 분리하고 있다. 웹앱만 단일 파일로 가면 저장소 안에 서로 다른 규칙이 공존한다.
- **Review 단계의 diff 가독성.** JS 약 350~400줄, CSS 약 200줄이 하나의 HTML에 섞이면 리뷰와 부분 수정이 어렵다.
- **파일이 3개여도 자체 완결성은 유지된다.** 상대 경로로만 링크하고 폴더 바깥 파일을 참조하지 않으므로, 폴더째 복사해도 그대로 돌아간다.

### 왜 ES 모듈이 아니라 클래식 스크립트인가

블로그 본체는 `type="module"`을 쓰지만, 여기서는 `<script src="game.js" defer></script>`로 한다.

- ES 모듈은 `file://`에서 CORS 정책으로 로드가 차단된다. 클래식 스크립트로 두면 로컬 HTTP 서버 없이 `index.html`을 더블클릭해도 동작하므로, 개발·검증·공유가 쉽다.
- 게임 로직은 하나의 응집된 상태 기계라 모듈로 쪼갤 실익이 없다. 전역 오염은 파일 전체를 IIFE로 감싸 막는다.

### `game.js` 내부 구획 (주석으로 구분)

| 구획 | 책임 |
|---|---|
| `CONFIG` | `SIZE = 4`, `WIN_VALUE = 2048`, `SPAWN_FOUR_RATE = 0.1`, `SWIPE_MIN_PX`, `STORAGE_KEY` |
| `state` | 순수 데이터. `grid`, `score`, `best`, `won`, `keepPlaying`, `over`, `snapshot` |
| 규칙 계층 | `lineIndices()`, `collapse()`, `move()`, `spawnTile()`, `hasMove()` — DOM을 모른다 |
| 저장 계층 | `safeStorage` (localStorage 래퍼) |
| 렌더 계층 | `buildBoard()`, `render()`, `announce()` — 상태를 읽기만 한다 |
| 입력 계층 | 키보드 / 포인터(스와이프) / 버튼 핸들러 |
| 부팅 | `init()` |

**규칙 계층이 DOM을 전혀 모르는 것이 이 설계의 핵심 제약이다.** 이 덕분에 Review 단계에서 콘솔로 `collapse([2,2,4,0])` 같은 순수 함수를 직접 호출해 규칙 버그를 검증할 수 있다. 그러려면 `collapse`와 `move`를 IIFE 안에 가두지 말고 검증용으로 `window.__2048 = { collapse, lineIndices, getState }` 정도만 노출한다(디버그 전용, 주석으로 명시).

## 2. 게임 규칙 정의

### 격자와 표현

- 4×4 = 16칸. 내부 표현은 **길이 16의 1차원 정수 배열**. `index = row * 4 + col`, `0`은 빈 칸.
  - 2차원 배열 대신 1차원을 쓰는 이유: 빈 칸 탐색·비교·스냅샷 복사가 `indexOf`, `slice`, 인덱스 순회로 단순해지고, 방향 처리에서 인덱스 매핑 한 줄로 끝난다.
- `SIZE`는 상수로 두고, 모든 순회는 `SIZE`를 참조한다. 4를 하드코딩하지 않는다.

### 새 타일 생성

- **시작 시 2개**를 빈 칸 중 무작위 위치에 생성한다.
- **값**: 90% 확률로 `2`, 10% 확률로 `4`. (`Math.random() < 0.1 ? 4 : 2`)
- **이동 후 1개**를 생성한다. 단, **격자가 실제로 변한 이동일 때만** 생성한다. 아무것도 움직이지 않은 방향키/스와이프에 타일이 생기면 플레이어가 벽에 대고 입력하는 것만으로 판을 채워 죽게 되는 심각한 규칙 버그다.

### 합치기 규칙

한 번의 이동에서:

1. 타일은 미는 방향의 벽 쪽으로 빈 칸을 메우며 이동한다.
2. **같은 값**의 두 타일이 이동 경로에서 만나면 합쳐져 값이 2배가 된다.
3. **한 이동에서 한 타일은 최대 한 번만 합쳐진다.** 이미 합쳐져 생긴 타일은 같은 이동 안에서 다시 합쳐지지 않는다.
   - 예: `[2,2,4,0]`을 왼쪽으로 → `[4,4,0,0]` (❌ `[8,0,0,0]` 아님)
   - 예: `[4,4,4,4]`를 왼쪽으로 → `[8,8,0,0]` (❌ `[16,0,0,0]` 아님)
4. **합치기 우선순위는 미는 방향의 벽에서 가까운 쌍부터**다.
   - 예: `[2,2,2,0]`을 왼쪽으로 → `[4,2,0,0]` (❌ `[2,4,0,0]` 아님)
   - 예: `[0,2,2,2]`를 오른쪽으로 → `[0,0,2,4]`

### 승리 판정

- 격자에 `2048` 타일이 처음 생기는 순간 승리. 승리 오버레이를 띄운다.
- 오버레이에는 **[계속하기]** 와 **[새 게임]** 두 버튼을 둔다. 계속하기를 누르면 `keepPlaying = true`가 되어 이후 판이 꽉 찰 때까지 계속 플레이할 수 있다.
- `won` 플래그로 **한 번만** 발동한다. 4096, 8192가 나올 때마다 다시 뜨면 안 된다.

### 패배 판정

**빈 칸이 하나도 없고 AND 인접한 같은 값 쌍이 하나도 없을 때** 게임 오버.

- 판정 시점: 새 타일을 생성한 **직후**. 생성 전에 판정하면 마지막 빈 칸이 채워진 상태를 놓친다.
- 인접 검사는 오른쪽·아래 두 방향만 보면 충분하다(모든 인접 쌍을 중복 없이 덮는다).
- 빈 칸이 있으면 인접 검사를 건너뛴다(조기 반환).

## 3. 핵심 알고리즘

### 네 방향을 하나의 연산으로 — 격자 회전 대신 인덱스 매핑

격자를 실제로 회전(transpose + reverse)시키는 방법도 널리 쓰이지만, 여기서는 **인덱스 매핑**을 택한다.

- 회전 방식은 이동마다 배열을 최대 4회 새로 만들고, 결과를 다시 역회전해야 하며, "합쳐진 칸의 위치"를 애니메이션용으로 원래 좌표로 되돌리는 과정에서 실수하기 쉽다.
- 인덱스 매핑은 **격자를 한 번도 회전시키지 않는다.** 방향마다 "어떤 순서로 칸을 읽을지"만 다르고, 읽고 쓰는 코드는 완전히 동일하다. 합쳐진 칸의 실제 보드 인덱스도 그대로 나온다.

#### `lineIndices(dir, lineNo)` → 길이 4의 보드 인덱스 배열

미는 방향의 **벽에서 가까운 순서**로 정렬해 반환한다. 이 "벽에서 가까운 순" 정렬이 합치기 우선순위 규칙(2-4)을 코드 한 줄 없이 자동으로 보장한다.

```
lineIndices(dir, n):   # n = 0..SIZE-1
  "left"  → [ n*SIZE + 0, n*SIZE + 1, n*SIZE + 2, n*SIZE + 3 ]      # n번째 행, 왼→오
  "right" → [ n*SIZE + 3, n*SIZE + 2, n*SIZE + 1, n*SIZE + 0 ]      # n번째 행, 오→왼
  "up"    → [ 0*SIZE + n, 1*SIZE + n, 2*SIZE + n, 3*SIZE + n ]      # n번째 열, 위→아래
  "down"  → [ 3*SIZE + n, 2*SIZE + n, 1*SIZE + n, 0*SIZE + n ]      # n번째 열, 아래→위
```

#### `collapse(values)` → `{ out, gained, mergedAt }`

입력은 벽에서 가까운 순으로 정렬된 길이 4의 값 배열. 출력도 같은 순서다.

```
compact ← values 중 0이 아닌 값만 순서 유지하며 추출
out ← []
gained ← 0
mergedAt ← []            # out 배열 안에서 합쳐져 생긴 칸의 위치
i ← 0
while i < compact.length:
    if i+1 < compact.length AND compact[i] == compact[i+1]:
        merged ← compact[i] * 2
        mergedAt.push(out.length)
        out.push(merged)
        gained ← gained + merged
        i ← i + 2                 # ★ 두 칸을 소비 — 이것이 이중 합치기를 원천 차단한다
    else:
        out.push(compact[i])
        i ← i + 1
out 뒤를 0으로 채워 길이 SIZE로 맞춘다
```

**`i ← i + 2`가 "한 이동에 같은 타일이 두 번 합쳐지지 않는다"는 규칙의 유일한 구현 지점이다.** 합쳐서 만든 `merged`는 `out`에만 들어가고 `compact`의 남은 부분과 다시 비교되지 않는다. 별도의 `blocked` 플래그나 병합 마킹 배열이 필요 없다.

#### `move(dir)` → `boolean` (격자가 변했는가)

```
changed ← false
gainedTotal ← 0
mergedBoardIndices ← []

for n in 0 .. SIZE-1:
    idxs   ← lineIndices(dir, n)
    values ← idxs.map(i => grid[i])
    { out, gained, mergedAt } ← collapse(values)

    for k in 0 .. SIZE-1:
        if grid[idxs[k]] != out[k]:
            grid[idxs[k]] ← out[k]
            changed ← true
    gainedTotal ← gainedTotal + gained
    for k in mergedAt: mergedBoardIndices.push(idxs[k])

return { changed, gainedTotal, mergedBoardIndices }
```

`mergedBoardIndices`는 애니메이션(합치기 팝)과 승리 판정에 쓴다.

#### 한 번의 입력이 처리되는 전체 흐름

```
handleMove(dir):
  if over: return
  snapshot ← { grid: grid.slice(), score, won, keepPlaying }   # ← 이동 전에 저장 (undo용)
  { changed, gainedTotal, mergedBoardIndices } ← move(dir)
  if not changed:
      snapshot ← null          # 무효 이동은 undo 대상이 아니다
      return                   # 타일도 생성하지 않는다
  score ← score + gainedTotal
  if score > best: best ← score; safeStorage.set(...)
  newIndex ← spawnTile()
  if not won and grid에 WIN_VALUE 존재:
      won ← true; 승리 오버레이 표시
  if not hasMove(): over ← true; 게임오버 오버레이 표시
  render(newIndex, mergedBoardIndices)
  announce()
```

#### `hasMove()`

```
if grid에 0이 있으면 return true
for r in 0..SIZE-1, c in 0..SIZE-1:
    if c+1 < SIZE and grid[r*SIZE+c] == grid[r*SIZE+c+1]: return true
    if r+1 < SIZE and grid[r*SIZE+c] == grid[(r+1)*SIZE+c]: return true
return false
```

## 4. 입력 처리

### 4-1. 키보드 (데스크톱)

- `keydown`을 **`document`가 아니라 게임 래퍼 요소(`#game`)에** 붙인다. `#game`에 `tabindex="0"`을 준다.
- 매핑: `ArrowLeft/Right/Up/Down`, 그리고 `a/d/w/s` (대소문자 무시). 방향키가 없는 배열의 키보드나 습관적 WASD 사용자를 함께 받는다.
- **방향키를 처리했으면 반드시 `event.preventDefault()`** 한다. 그러지 않으면 iframe 문서 자체가 스크롤되어 판이 위아래로 흔들린다.
- 방향키가 아닌 키에는 `preventDefault`를 걸지 않는다. Tab 이동을 막으면 접근성이 깨진다.
- `event.repeat`인 이벤트도 그대로 처리한다(길게 누르면 연속 이동). 다만 오버레이가 떠 있을 때는 이동을 무시한다.

### 4-2. iframe 안에서의 키보드 포커스 — 반드시 다룰 문제

iframe에 임베드되면 **부모 페이지가 포커스를 갖고 있는 동안 방향키가 게임에 전달되지 않는다.** 사용자는 "방향키가 안 먹는다"고 느낀다. 대책:

1. `#game`에 `tabindex="0"`을 주고, 보드 영역에 `pointerdown` 발생 시 `#game.focus({ preventScroll: true })`를 호출한다. **탭/클릭 한 번으로 포커스가 잡힌다.**
2. 포커스가 없을 때만 보이는 안내 문구를 둔다: "화면을 한 번 누른 뒤 방향키로 움직이세요." `focus`/`blur` 이벤트로 `#game`의 `data-focused` 속성을 토글하고 CSS로 표시를 제어한다.
3. **`autofocus`는 쓰지 않는다.** iframe이 로드되자마자 포커스를 뺏으면 부모 블로그 페이지가 게임 위치로 강제 스크롤된다.
4. `:focus-visible`로 래퍼에 명확한 아웃라인을 준다. 포커스가 어디 있는지 눈에 보여야 한다.

### 4-3. 터치 스와이프 (모바일) — 필수

휴대폰에는 방향키가 없으므로 스와이프가 유일한 조작 수단이다.

**Pointer Events를 쓴다** (`pointerdown` / `pointerup` / `pointercancel`). 이유: 터치·펜·마우스를 한 코드로 처리하고, 데스크톱에서 마우스 드래그로도 조작할 수 있게 되며, `touch` + `mouse` 이벤트 중복 발화 문제가 없다.

```
onPointerDown(e):
  if activePointerId != null: return          # 멀티터치 무시 — 첫 포인터만 추적
  if e.pointerType == "mouse" and e.button != 0: return
  activePointerId ← e.pointerId
  startX ← e.clientX; startY ← e.clientY; startT ← e.timeStamp
  board.setPointerCapture(e.pointerId)        # 손가락이 보드 밖으로 나가도 up을 받는다
  focusGame()

onPointerUp(e):
  if e.pointerId != activePointerId: return
  dx ← e.clientX - startX
  dy ← e.clientY - startY
  activePointerId ← null
  threshold ← max(24, board.clientWidth * 0.06)
  if max(|dx|, |dy|) < threshold: return      # 탭이지 스와이프가 아니다
  if |dx| > |dy|: dir ← dx > 0 ? "right" : "left"
  else:           dir ← dy > 0 ? "down"  : "up"
  handleMove(dir)

onPointerCancel(e): activePointerId ← null
```

설계 근거:

- **임계값은 고정 픽셀이 아니라 보드 폭 비율(6%)에 하한 24px**을 둔다. 작은 화면에서는 짧은 스와이프도 의도로 인정하고, 큰 화면에서는 손 떨림을 무시한다.
- **축 판정은 `|dx|`와 `|dy|`의 단순 비교**로 충분하다. 대각선 스와이프도 더 큰 성분 쪽으로 확정 해석되므로 "아무 일도 안 일어나는" 답답함이 없다.
- **`pointerup`에서 한 번만 판정한다.** `pointermove` 중에 방향을 확정하면 한 번의 긴 스와이프가 여러 이동으로 쪼개질 수 있다.
- 속도(플릭) 판정은 넣지 않는다. 거리 임계값만으로 오작동이 충분히 걸러지고, 느리게 미는 사용자를 배제하지 않는다.

### 4-4. 스와이프로 페이지가 스크롤되는 문제 — 4중 방어

가장 흔한 모바일 실패 지점이다. CSS와 JS를 함께 쓴다.

1. **`touch-action: none;`을 보드 요소에 준다.** 이것이 1차 방어이자 정공법이다. 브라우저가 그 영역의 터치를 스크롤·핀치 제스처로 소비하지 않고 전부 스크립트에 넘긴다.
2. **`touchmove`에 `{ passive: false }` 리스너를 붙이고 `preventDefault()`** 한다. `touch-action`을 인식하지 못하는 구형 브라우저 대비 2차 방어다. 리스너를 **보드에만** 붙인다(문서 전체에 붙이면 점수판·버튼 주변 스크롤까지 죽는다).
3. **`overscroll-behavior: contain;`을 `html, body`에 준다.** iframe 끝에서 스크롤이 부모 페이지로 전파되는 체이닝과 iOS 당겨서 새로고침을 막는다.
4. **보드에 `user-select: none`, `-webkit-user-select: none`, `-webkit-tap-highlight-color: transparent`.** 스와이프 중 숫자가 드래그 선택되거나 회색 하이라이트가 번쩍이는 것을 막는다.

버튼(다시 시작/실행 취소)에는 `touch-action: manipulation`을 주어 더블탭 확대만 없애고 탭은 정상 동작시킨다. **`user-scalable=no`는 쓰지 않는다** — 확대를 막는 것은 접근성 위반이고, 위 조치들로 이미 필요한 만큼 해결된다.

viewport 메타는 `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">`.

## 5. 점수 처리

### 계산

- **한 이동에서 합쳐져 생긴 타일 값들의 합**을 점수에 더한다. `2+2 → 4`면 +4, `[4,4,4,4]`를 밀어 `[8,8]`이 되면 +16.
- 이동만 하고 합치기가 없으면 점수는 0점 증가.
- 새로 생성되는 타일은 점수에 포함하지 않는다.

### 최고 점수 — `localStorage`에 저장한다

키: `"apps.2048.best"` (블로그의 `"theme"` 키와 충돌하지 않도록 네임스페이스를 붙인다).

**저장이 막힌 환경에서도 게임이 반드시 동작해야 한다.** iframe 샌드박스, Safari 프라이빗 모드, 서드파티 스토리지 차단, 브라우저 설정에 따라 `localStorage`는 **접근하는 순간 예외를 던질 수 있다**(값을 읽을 때만이 아니라 `window.localStorage` 프로퍼티 접근 자체에서 `SecurityError`). 따라서 파싱만 감싸는 것으로는 부족하다.

```
safeStorage:
  memory ← {}                       # 폴백 저장소
  get(key):
    try   { v ← window.localStorage.getItem(key); return v }
    catch { return memory[key] ?? null }
  set(key, value):
    try   { window.localStorage.setItem(key, value) }
    catch { memory[key] ← value }   # 조용히 세션 메모리에 보관
```

- 읽어온 값은 `Number(...)`로 변환한 뒤 **`Number.isFinite`와 `>= 0` 검사**를 통과할 때만 채택한다. 실패하면 `0`. 손상되거나 조작된 값이 `NaN`으로 화면에 뜨는 것을 막는다.
- 저장 실패는 **에러 메시지를 띄우지 않는다.** 게임은 정상 진행되고 최고 점수만 새로고침 시 초기화된다. 이 상황을 사용자에게 알려봐야 할 수 있는 일이 없다.
- 최고 점수 저장은 **갱신될 때만** 호출한다(매 이동마다 쓰지 않는다).
- 최고 점수는 **다시 시작해도 초기화하지 않는다.** 별도의 초기화 UI는 두지 않는다(오조작 위험 대비 가치가 낮다).

### 점수 표시 연출

점수가 오르면 `+16` 같은 작은 텍스트가 점수판 위로 떠오르며 사라지는 연출을 넣는다. CSS 애니메이션 하나로 끝나고, 어떤 이동이 몇 점이었는지 즉시 알려주는 효과가 크다. `prefers-reduced-motion`에서는 생략한다.

## 6. 화면 구성과 스타일

### 레이아웃

```
┌─────────────────────────────────┐
│  2048            [현재]  [최고]  │   헤더: 제목 + 점수판 2개
│  타일을 합쳐 2048을 만드세요      │
│                    [↩] [새 게임]  │   실행 취소 / 다시 시작
├─────────────────────────────────┤
│  ┌───┬───┬───┬───┐              │
│  │   │ 2 │   │   │              │   보드 (정사각형, 4×4)
│  ├───┼───┼───┼───┤              │
│  │   │   │ 4 │   │              │   ← 오버레이가 이 위를 덮는다
│  └───┴───┴───┴───┘              │
├─────────────────────────────────┤
│  방향키 또는 스와이프로 조작       │   안내 문구 + aria-live 영역
└─────────────────────────────────┘
```

- 마크업: `#game > (header.hud, div.board, footer.hint)`. 보드 안에는 **16개의 `.cell` 요소를 한 번만 생성**한다.
- **셀과 타일을 분리하지 않는다.** 하나의 `.cell` 요소가 `data-value` 속성으로 빈 칸(`0`)과 타일 상태를 모두 표현한다. 이동마다 DOM을 다시 만들지 않고 `data-value`와 `textContent`만 갱신한다. 셀 개수가 16개로 고정이라 이 방식으로 충분하고, 요소 재생성이 없어 CSS 전이도 안정적으로 걸린다.

### 크기 정책 — iframe 임베드 전제

**고정 픽셀을 쓰지 않는다.** 컨테이너 폭에 맞춰 늘어나야 한다.

- `html, body { height: 100%; margin: 0; }`, 앱 루트는 `min-height: 100dvh` (미지원 대비 `100vh`를 먼저 선언하고 `100dvh`로 덮어쓴다). iOS 주소창 때문에 아래가 잘리는 문제를 막는다.
- `#game { width: 100%; max-width: 28rem; margin-inline: auto; padding: clamp(0.75rem, 3vw, 1.25rem); }`
- `.board { width: 100%; aspect-ratio: 1 / 1; display: grid; grid-template-columns: repeat(4, 1fr); gap: clamp(6px, 2%, 12px); }`
  - `aspect-ratio`로 정사각형을 유지하므로 JS로 크기를 계산할 필요가 없다.
  - **세로가 짧은 경우 대비**: `.board { max-height: min(100%, 60dvh); max-width: 60dvh; }` 를 함께 주어 가로로만 커지다 화면 아래로 넘치는 것을 막는다.
- **타일 글자 크기는 컨테이너 쿼리 단위로 정한다.** `.board { container-type: inline-size; }` 후 `.cell { font-size: 9cqw; }`. 뷰포트가 아니라 **보드 자신의 폭**에 비례해야 iframe 안에서 정확히 맞는다.
  - 폴백: `@supports not (container-type: inline-size)` 블록에서 `font-size: clamp(1rem, 6vw, 2rem)`.
  - 자릿수가 많은 타일은 축소한다: `[data-value="128"]~ → 7cqw`, `1024` 이상 → `5.5cqw`.
- `padding-bottom: env(safe-area-inset-bottom)`으로 iOS 홈 인디케이터 영역을 피한다.
- 앱 전체가 **스크롤 없이** 한 화면에 들어가는 것을 목표로 한다.

Embed 단계 권장 마크업(참고):
```html
<iframe src="apps/2048/index.html" title="2048 게임"
        style="width:100%; max-width:26rem; aspect-ratio:3/4; border:0; border-radius:8px"
        loading="lazy"></iframe>
```

### 타일 색상 규칙

값이 커질수록 배경이 진해지고 따뜻해진다. `.cell[data-value="N"]` 선택자로 지정한다.

| 값 | 배경 | 글자 |
|---|---|---|
| 0 (빈 칸) | 보드보다 약간 밝은 톤 | — |
| 2 | 가장 옅은 크림 | 어두운 글자 |
| 4 | 옅은 베이지 | 어두운 글자 |
| 8 | 연한 주황 | 밝은 글자 |
| 16 / 32 / 64 | 주황 → 진한 주황 → 붉은 주황 | 밝은 글자 |
| 128 / 256 / 512 | 노랑 계열, 점점 채도 상승 | 밝은 글자 |
| 1024 / 2048 | 가장 진한 금색, 은은한 발광 그림자 | 밝은 글자 |
| 2048 초과 | **`data-big` 속성** 하나로 단일 짙은 색 | 밝은 글자 |

**2048 초과 처리 원칙**: 4096, 8192…마다 색을 추가하지 않는다. 렌더 시 값이 `WIN_VALUE`를 넘으면 `data-big="true"`를 붙이고 하나의 스타일을 공유한다. CSS가 무한히 늘어나는 것을 막는다.

- 2와 4만 어두운 글자, 8 이상은 밝은 글자 — 명도 대비 4.5:1 이상을 각 조합에서 확인한다.
- 색은 CSS 변수(`--t2`, `--t4`, …)로 선언해 다크 모드에서 값만 바꾼다.

### 다크 모드 — 자체 팔레트 + `prefers-color-scheme`

**결정: 블로그의 CSS 파일을 참조하지 않고 자체 팔레트를 갖되, `@media (prefers-color-scheme: dark)`로 스스로 대응한다. 추가로 `?theme=light|dark` 쿼리 파라미터 오버라이드를 지원한다.**

근거:
- CLAUDE.md의 "웹앱은 자체 완결" 규칙상 `css/tokens.css`를 직접 링크할 수 없다. 링크하면 폴더째 복사했을 때 깨진다.
- 블로그는 사용자가 토글한 테마를 `localStorage["theme"]`에 저장한다. 같은 오리진이라 iframe에서 읽을 수는 있지만, 그것은 **파일 의존이 아닌 암묵적 계약 의존**이고 블로그가 키 이름을 바꾸면 조용히 깨진다. 대신 Embed 단계에서 `?theme=dark`를 붙이는 명시적 방법을 제공한다.
- 다크 모드 팔레트는 밝은 팔레트를 그대로 어둡게 하지 않는다. 배경은 블로그와 어울리도록 `#181a1e` 계열, 타일은 채도를 약간 낮춰 눈부심을 줄인다.
- **런타임 실시간 동기화(블로그에서 테마를 토글하면 iframe도 즉시 바뀌는 것)는 이번 범위에서 제외한다.** `postMessage` 채널이 필요해 자체 완결성과 복잡도 대비 가치가 낮다. 필요해지면 Embed 단계에서 별도로 다룬다.

### 애니메이션 — 넣는다, 단 "슬라이딩은 제외"

**결정: 새 타일 등장(scale-in)과 합치기 팝(scale bounce), 점수 증가 플로트만 넣는다. 타일이 미끄러지는 이동 애니메이션은 넣지 않는다.**

근거:
- **슬라이딩은 비용이 크다.** 타일마다 고유 id를 부여해 이동 전후 위치를 추적하고, 격자 대신 절대 위치 배치로 바꾸고, 합쳐지는 두 타일이 같은 칸에 겹쳤다가 하나로 바뀌는 중간 상태를 관리해야 한다. 데이터 모델(1차원 값 배열)이 타일 객체 배열로 바뀌어야 하고, 구현·검증 분량이 대략 두 배가 된다.
- **반면 등장/합치기 연출은 CSS 15줄이면 되고**, 피드백 가치의 대부분을 가져간다. "내 입력이 처리됐다", "여기서 합쳐졌다"를 즉시 알려주는 것이 핵심이고, 그건 도착점의 팝 하나로 충분하다.
- 구현: 렌더 시 새 타일 인덱스에 `.is-new`, 합쳐진 인덱스에 `.is-merged` 클래스를 추가하고 `animationend`에서 제거한다. 애니메이션은 120~160ms로 짧게.
- **`@media (prefers-reduced-motion: reduce)`에서 모든 애니메이션과 전이를 `none`으로 끈다.**

### 격자 크기 — 4×4 고정 (단, 상수화)

**결정: UI로 크기를 고를 수 없게 한다. 다만 코드에서 `SIZE = 4` 상수를 쓰고 4를 하드코딩하지 않는다.**

근거: 크기 선택 UI를 넣으면 선택기 UI, 크기별 최고 점수 분리 저장, 크기별 승리 목표값 재정의, CSS 그리드 동적 변경이 줄줄이 따라온다. 2048의 정체성은 4×4이고 사용자 요청에도 없었다. 다만 알고리즘을 `SIZE` 기반으로 짜두면 나중에 상수 하나와 CSS 변수 하나만 바꿔 3×3/5×5로 확장할 수 있으므로, **지금 비용 없이 미래를 열어두는 쪽**을 택한다.

### 실행 취소 — 넣는다, 1단계만

**결정: 직전 한 수만 되돌리는 [↩ 되돌리기] 버튼을 넣는다. 연속 undo는 불가.**

근거:
- 모바일에서 스와이프 오조작은 흔하고 치명적이다(의도치 않은 한 수로 판이 무너진다). 되돌리기가 없으면 터치 조작의 체감 품질이 크게 떨어진다.
- 비용이 거의 없다. 이동 **직전** 상태(`grid.slice()`, `score`, `won`, `keepPlaying`) 하나를 변수에 담아두고 복원하면 끝이다. 전체 히스토리 스택이 아니라 **단일 스냅샷**이므로 메모리·복잡도가 사실상 0이다.
- 1단계로 제한하는 이유: 무제한 undo는 시행착오로 최적해를 찾는 치트가 되어 점수의 의미를 없앤다. 실수 복구는 되고 완전 탐색은 안 되는 지점이 1단계다.
- 규칙: 되돌린 직후 스냅샷은 `null`이 되어 버튼이 비활성(`disabled`)된다. 격자가 변하지 않은 무효 이동은 스냅샷을 남기지 않는다. 게임 오버 상태에서도 되돌리기는 허용한다(마지막 실수 복구가 가장 필요한 순간이다). 새 게임을 시작하면 스냅샷을 비운다.
- 키보드 단축키는 배정하지 않는다(`Ctrl+Z`는 브라우저 기본 동작과 충돌 소지가 있다). 버튼만 제공한다.

## 7. 접근성과 상태 표시

### 게임 오버 / 승리 표시

- 보드 위를 덮는 반투명 오버레이. `position: absolute; inset: 0;`
- **승리**: "2048 달성!" + 최종 점수 + `[계속하기]` `[새 게임]`
- **게임 오버**: "더 이상 움직일 수 없습니다" + 최종 점수 + (최고 기록 경신 시) "최고 기록!" + `[되돌리기]` `[새 게임]`
- 오버레이가 열리면 **주 버튼으로 포커스를 옮긴다.** 키보드 사용자가 Tab을 헤매지 않는다.
- 오버레이가 열려 있는 동안 방향키/스와이프 이동은 무시한다.
- 오버레이는 `hidden` 속성으로 토글한다(`display:none`만 쓰면 스크린 리더가 내용을 읽어버릴 수 있다).

### 다시 시작

- `<button type="button">새 게임</button>`. `div`에 클릭 핸들러를 다는 방식은 쓰지 않는다.
- 진행 중 실수로 눌러 판이 날아가지 않도록, **점수가 0보다 클 때만** `confirm()` 대신 인라인 확인 상태(버튼 라벨이 "정말 새 게임?"으로 바뀌고 한 번 더 눌러야 실행, 3초 후 원복)를 쓴다. `confirm()`은 iframe 안에서 부모 페이지까지 블로킹해 경험이 나쁘다.

### 스크린 리더 / 라이브 영역

- `<p class="sr-only" role="status" aria-live="polite">`를 두고, 이동 후 갱신한다: `"점수 128점, 빈 칸 6개"`. 이동마다 16칸을 다 읽으면 소음이므로 **요약만** 전한다.
- 게임 오버·승리는 같은 영역에 `"게임 종료. 최종 점수 1234점"`으로 알린다. `aria-live="assertive"`는 쓰지 않는다(사용자의 다른 작업을 끊는다).
- 각 셀에 `aria-hidden="true"`를 주어 숫자 16개가 개별로 읽히는 것을 막고, 판 상태는 라이브 영역 문구로 전달한다.
- 점수판 숫자에는 `<span class="sr-only">현재 점수</span>` 같은 레이블을 붙인다. 숫자만 두 개 나란히 있으면 무엇인지 알 수 없다.
- `.sr-only` 유틸리티 클래스를 직접 정의한다(외부 리셋에 의존하지 않는다).

### 포커스

- `#game[tabindex="0"]`이 유일한 게임 진입 포커스 지점. 16개 셀은 포커스 대상이 아니다.
- `:focus-visible` 아웃라인을 명확히(2px, 오프셋 2px). `outline: none`만 주고 대체 표시를 안 하는 실수를 하지 않는다.
- 탭 순서: `#game` → 되돌리기 → 새 게임. 자연스러운 DOM 순서로 두고 `tabindex` 양수는 쓰지 않는다.
- `lang="ko"`, `<title>2048</title>` 지정.

## 8. 검증 항목 (Review 단계 체크리스트)

### A. 규칙 정확성 — 순수 함수 단위 검증

`window.__2048.collapse()`를 콘솔에서 직접 호출해 확인한다. **입력은 "미는 방향의 벽에서 가까운 순"으로 정렬된 배열**임에 유의.

| # | 입력 | 기대 출력 | 확인하는 것 |
|---|---|---|---|
| 1 | `[2,2,4,0]` | `[4,4,0,0]`, gained 4 | **이중 합치기 금지** — `[8,0,0,0]`이 나오면 버그 |
| 2 | `[4,4,4,4]` | `[8,8,0,0]`, gained 16 | 이중 합치기 금지 + 두 쌍 동시 처리 |
| 3 | `[2,2,2,0]` | `[4,2,0,0]`, gained 4 | **벽에 가까운 쌍 우선** — `[2,4,0,0]`이면 버그 |
| 4 | `[2,0,2,2]` | `[4,2,0,0]`, gained 4 | 빈 칸 건너뛴 뒤 합치기 + 우선순위 |
| 5 | `[0,0,0,2]` | `[2,0,0,0]`, gained 0 | 이동만, 점수 증가 없음 |
| 6 | `[2,4,2,4]` | `[2,4,2,4]`, changed=false | 합칠 것 없는 꽉 찬 줄 |
| 7 | `[0,0,0,0]` | `[0,0,0,0]`, changed=false | 빈 줄 |
| 8 | `[4,4,2,2]` | `[8,4,0,0]`, gained 12 | 서로 다른 두 쌍 |
| 9 | `[2,2,2,2]` | `[4,4,0,0]`, gained 8 | 점수 = 합쳐진 값의 합 |

**이중 합치기는 이 게임에서 가장 흔하고 가장 치명적인 규칙 버그다.** 위 1·2·3번을 반드시 통과해야 한다. 실제 판에서도 재현: 한 행을 `2 2 4 _`로 만들고 왼쪽으로 밀어 `4 4`가 되는지 눈으로 확인.

### B. 무효 이동

- [ ] 이미 왼쪽 벽에 붙은 판에서 왼쪽 방향키를 눌러도 **새 타일이 생기지 않는다.** (가장 놓치기 쉬운 버그)
- [ ] 무효 이동 후 점수가 오르지 않는다.
- [ ] 무효 이동 후 되돌리기 버튼이 활성화되지 않는다.
- [ ] 왼쪽 방향키를 20번 연타해도 판이 채워지지 않는다.

### C. 방향 대칭성

- [ ] 좌/우/상/하 네 방향이 모두 동일한 규칙으로 동작한다.
- [ ] 특정 대칭 배치를 만들어 상↔하, 좌↔우 결과가 거울처럼 대응하는지 확인한다.
- [ ] `lineIndices`가 반환한 인덱스에 중복이 없고, 네 방향 모두 16개 인덱스를 정확히 한 번씩 덮는다.

### D. 승리 / 패배

- [ ] `1024 1024`를 만들어 합치면 승리 오버레이가 뜬다.
- [ ] [계속하기] 후 게임이 이어지고, **4096을 만들어도 승리 오버레이가 다시 뜨지 않는다.**
- [ ] 판이 꽉 찼지만 인접한 같은 값이 있으면 게임 오버가 **아니다.**
- [ ] 판이 꽉 차고 인접 쌍이 전혀 없을 때만 게임 오버.
- [ ] 게임 오버 판정이 새 타일 생성 **직후**에 이뤄진다(마지막 빈 칸이 채워지는 경우를 놓치지 않는다).

### E. 점수 / 저장

- [ ] 점수가 합쳐진 타일 값의 합과 정확히 일치한다(A-9번 케이스로 확인).
- [ ] 최고 점수가 새로고침 후에도 유지된다.
- [ ] 새 게임을 눌러도 최고 점수는 유지된다.
- [ ] **개발자 도구에서 `localStorage`를 차단하거나 Safari 프라이빗 모드에서 열어도 게임이 정상 동작하고 콘솔 에러가 없다.**
- [ ] `localStorage`의 best 값을 `"abc"`로 손상시켜도 `NaN`이 화면에 뜨지 않는다.

### F. 모바일 — 실기기 또는 기기 에뮬레이션 필수

- [ ] 네 방향 스와이프가 모두 동작한다.
- [ ] **스와이프 중 페이지가 스크롤되지 않는다.** (가장 중요)
- [ ] iOS 당겨서 새로고침이 발동하지 않는다.
- [ ] 보드를 더블탭해도 확대되지 않고, 두 손가락 확대는 여전히 가능하다.
- [ ] 스와이프 중 숫자 텍스트가 드래그 선택되지 않는다.
- [ ] 짧은 탭(임계값 미만)으로는 타일이 움직이지 않는다.
- [ ] 두 손가락으로 동시에 스와이프해도 한 번만 이동한다.
- [ ] 세로 좁은 화면(360×640)과 가로 모드에서 판이 잘리거나 스크롤이 생기지 않는다.

### G. iframe 임베드

- [ ] 임시 HTML에 iframe으로 넣고, **iframe을 한 번 탭/클릭한 뒤 방향키가 동작한다.**
- [ ] 포커스 전에는 "눌러서 시작" 안내가 보이고, 포커스 후에는 사라진다.
- [ ] 방향키를 눌렀을 때 **부모 페이지도, iframe 내부도 스크롤되지 않는다.**
- [ ] 페이지 로드 시 iframe이 포커스를 뺏어 부모 페이지가 튀지 않는다.
- [ ] iframe 폭을 320px~600px로 바꿔도 보드가 정사각형을 유지하고 글자 크기가 함께 조정된다.

### H. 접근성

- [ ] 마우스 없이 키보드만으로 전체 조작(플레이, 되돌리기, 새 게임)이 가능하다.
- [ ] 포커스 위치가 항상 눈에 보인다.
- [ ] 오버레이가 열리면 포커스가 오버레이 버튼으로 이동한다.
- [ ] `prefers-reduced-motion: reduce`에서 애니메이션이 꺼진다.
- [ ] 모든 타일 값에서 글자/배경 대비가 4.5:1 이상이다.
- [ ] 다크 모드에서도 대비가 유지된다.
- [ ] 스크린 리더 라이브 영역이 이동 후 점수를 알린다.

### I. 코드 / 구조

## 9. 구현 순서 (Build 단계 권장)

1. **`index.html` 골격** — 마크업 구조와 메타 태그. 스타일 없이 요소만.
2. **규칙 계층** — `lineIndices`, `collapse`, `move`, `spawnTile`, `hasMove`. DOM 없이 콘솔로 A절 9개 케이스를 먼저 통과시킨다. **여기서 규칙을 확정하고 넘어간다.**
3. **렌더 계층** — 16개 셀 생성, `render()`로 `data-value` 갱신. 키보드 입력만 붙여 플레이 가능 상태 확인.
4. **CSS** — 그리드, `aspect-ratio`, 타일 팔레트, 컨테이너 쿼리 글자 크기.
5. **터치 입력 + 스크롤 방어** — `touch-action`, 포인터 이벤트, `overscroll-behavior`. **실기기 또는 기기 에뮬레이션으로 즉시 확인.**
6. **점수 + `safeStorage`**
7. **승리/패배 오버레이, 되돌리기, 새 게임**
8. **다크 모드, 애니메이션, 접근성 마감**
