## 2. 뒤집은 결정과 이유 (18절 표에 옛 결정·이유 기록)

1. **자동 번역의 경계**: "탭한 줄의 문단만" → "지금 듣는 쪽 + 다음 한 쪽, 낭독 중일 때만". Nour 의 확인된 요구("읽으면서 각 줄을 소리 내어 번역")가 탭 방식과 양립하지 않는다. 전체·장 단위 선번역은 여전히 없다.
2. **번역 표시 위치**: 줄 아래 인라인 블록 → 두 뷰 공통 **하단 자막 띠**. 문장마다 번역이 바뀌면 인라인은 본문을 문장마다 오르내리게 하고(눈 피로), 문장 끝 삽입은 줄 span 텍스트 노드를 쪼개 10a 하이라이트·6a 이음새 문제를 다시 연다. 원본 뷰는 어차피 하단.
3. **쪽을 넘는 문장 이어 붙이기(7-2 `continuesNext`)** 폐지: 낭독 큐가 쪽마다 따로라 이어 붙이면 번역 1 ↔ 발화 2 가 된다. 조각은 `frag` 표시로 번역.
4. **원문 언어 `'en'` 고정** → `documents.lang`(추정 + 사용자 변경).
5. **캐시 상한 50MB → 200MB**: 50MB 는 약 1,250쪽 `[추정]` 에서 옛 번역을 지워 재독 시 비용이 다시 난다.
6. **요약 기능 후순위**(사용자 결정 — 아래 3-B).

판단해서 정한 것(묻지 않음): 기본 모드 `speak`(번역 표시 + 번역문 낭독), 선행 요청 시점 = 지금 쪽 발화 절반 지점, 냉시작 head 600자, 번역문 대기 상한 4초 후 건너뜀(되돌아가 읽지 않음), 줄 단위 낭독에서는 동반 번역 쉼, `LanguageDetector` 미사용(휴리스틱 한 경로), 쪽당 호출 수 표시, 번역문 속도는 원문과 공유.

## 3. 사용자에게 물어야 할 것 (3개)

### 질문 1. `speak` 모드에서 **원문(영어)도 소리 내어 읽을까?**
- (가) **영어 → 아랍어** 순서로 둘 다 읽기 — 쪽당 약 17분 `[추정]`(원문만의 약 2.4배)
- (나) **아랍어만** 읽고 영어는 하이라이트만 — 약 10분(약 1.4배). 영어 발음을 귀로 듣지 못한다
- **권장: (가)를 기본**, (나)는 속도 팝오버에서 한 번 탭(`readalong.speakSource`). 근거: "책을 읽으면서 … 번역"은 앱이 원서를 읽는 기존 기능 위에 번역을 얹는 것으로 읽히고, B1 학습자에게 원문 발음이 함께 가는 편이 학습 목적(1절)에 맞다. 다만 "읽으면서"가 **Nour 가 눈으로 읽는다**는 뜻이면 (나)가 맞다 — 이 해석은 Nour 만 안다. 어느 답이든 기본값 한 줄만 바뀐다.

### 질문 2. 시리아 실호출 확인(16-D0 `[M]`)에 **누구의 키**를 쓸까?
- (가) Nour 본인의 AI Studio 키 — BYOK 원칙 그대로. 단, 시리아에서 **키 발급 자체가 막힐 수** 있다 `[가정]`(그러면 그것이 이미 지역 제한의 답이다)
- (나) 운영자 키를 Nour 기기에 **한 번만** 넣어 시험하고 지운다 — "키 발급"과 "API 호출 지역"을 분리해 볼 수 있다. 키를 남에게 건네는 위험·운영자 할당량 소모가 있다
- **권장: (가) 먼저, 발급 단계에서 막히면 (나)로 1회 시험.** 키 입력은 어느 경우든 사람이 직접 한다(에이전트는 실제 키를 넣지 않는다).

### 질문 3. 지역 제한(`REGION`)이 **확인되면** 무엇을 할까? (7b 결과 전에 방향만)
- (가) **무료 BYOK 대안부터 시험** — OpenRouter `:free`·Mistral 실험 티어(8-2 표에 이미 있음, 10단계 openai-compat 작업). 비용 0원 원칙 유지. 이들의 시리아 지역 정책도 `[가정]`
- (나) **xAI Grok**(`https://api.x.ai/v1`) — Nour 가 이미 쓴다. 무료 여부 `[가정]`, 유료면 **"사용자 비용 0원" 원칙과 충돌**
- (다) 앱은 그대로 두고 네트워크 쪽 해결(VPN 등)은 Nour 의 선택에 맡긴다 — 앱은 안내하지 않는다
- **권장: (가) → 안 되면 (나)를 비용 확인 후.** (다)는 앱 설계 밖이라 따로 정할 것이 없다. 이 답에 따라 19절 "지역 제한 시 대안" 행의 순서가 정해진다.

### 3-B. 결정된 것 (질문 목록에서 뺐다)
- **요약 기능(7-3·10-3·16-D 요약 항목) 후순위** — 사용자 결정(추가 지침 3). 이유: NotebookLM 이 자료 전체 요약·질문을 이미 하고, 무료 한도를 낭독 동반 번역에 몰아 쓴다. 7-3·10-3 은 `[후순위 2026-09-28]` 표시로 설계 보존, 16-D5 로 기준 이동, 19절에서 7b·8 단계 밖. 8a 파이프라인은 `kind` 확장 여지 유지.
- **"GROOC" = xAI Grok** 확정(추가 지침 2) → 8-2 표·19절에 `xai` 위치만. CORS·무료 여부·시리아 제한 전부 `[가정]`.
- **NotebookLM·Copilot 연동 안 함** — 공개 BYOK API 없음. 역할 분담은 17절: NotebookLM = 자료 전체 질문·요약·오디오 개요 / MedReader = 한 문장씩 낭독 + 하이라이트 + 그 문장의 번역, 리플로우, 오프라인, 원서 퀴즈.
- **의학 사이트 계정(장학금, 약 3주 뒤)** — 앱은 입력받거나 저장하지 않는다(12-7·13절 유료 DB 행). 새 기능 설계 없음.
- 참고: Nour 가 시리아에서 NotebookLM 을 쓴다는 것은 Gemini **API** 가능성에 대한 **약한** 긍정 신호일 뿐이다(8-2). 결론은 Nour 기기 실호출.

## 5. 코드를 읽다 발견한 것 (spec 에 반영함)

- **표 안내 발화가 원서 음성으로 읽힌다.** `insertTableNotices` 가 UI 언어 문장을 큐에 끼우는데 `speakAt` 은 모든 발화에 `utt.lang = docLang`(en-US)을 준다 — UI 가 아랍어면 영어 음성이 아랍어를 읽는다. 6-1 에 "표 안내는 UI 언어 음성으로"를 적고 8b 범위에 넣었다.
- `flowParas()` 결과에는 표 안내 문단(`kind: 'table-notice'`)이 섞인다 — 번역 입력에서 빼야 한다. `sentencesOf` 가 뺀다(7-8-2).
- 서재 카드에는 [⋯] 가 **없다**([이어 읽기]·[삭제]뿐). 12-6 에 [⋯] 신설을 명시했다(원문 언어만).
- 설정·사용량 화면은 아직 자리표시자(`index.html`). 7b 가 설정 화면을 처음 만든다.
- `describePage`·`flowParas` 는 `ui/reader.js` 에 있어 서비스가 import 할 수 없다 → 다음 쪽 문단은 UI 가 `loadParas` 로 주입하고, `flowParasOf` 를 순수 함수로 떼어 두 경로가 같은 함수를 지나게 했다(8a).

## 6. 요청(질문 아님)

- **프랑스어·한국어 원서 표본**이 생기면 한 권씩 받고 싶다. 7c 는 경로만 열고, 추출 품질(4절)·문장 분할 규칙(`fr`·`ko` 는 `[가정]`)은 실물 측정 후에 정한다.

### 7-2. 지침과 다르게 정한 것 하나 — `READ_AHEAD_CHARS` 기본값

지침은 "기본 = `MAX_REQ_CHARS`(6,000)"였는데 **9,000자(= 1.5배)** 로 두었다. 둘이 같으면 산수가 맞지 않는다: 창을 커서부터 6,000자로 두고 "현재 청크의 절반을 발화했을 때 다음 청크"를 보내면, 그때 창에 남은 빈자리가 3,000자뿐이라 **청크가 늘 반쪽**이 되고 호출 수가 약 2배(CMDT 2021 ≈ 3,200회)가 된다. 청크를 꽉 채우려면 창 = 청크 + 선행 여유(청크의 절반)여야 한다. 상수는 `READ_AHEAD_FACTOR: 1.5` 로 두어 `ai.maxReqChars` 와 숫자를 두 곳에 두지 않았다. 창을 6,000자로 엄격히 두고 싶다면 대안은 두 가지다. 하나는 선행 요청을 "현재 청크를 다 읽은 뒤"로 미루는 것이다. 그러면 청크 경계마다 냉시작처럼 기다리게 된다. 다른 하나는 창을 "현재 청크 + 다음 청크"로 정의하는 것이다. 이것은 `{p, p+1}` 을 글자로 옮긴 모양이다. **오케스트레이터가 뒤집을 수 있게 18절 행에 이유를 적어 두었다.**

### 7-3. 새로 생긴 위험

- **여러 쪽 `loadParas`**: 쪽이 작은 책은 청크 하나에 약 3~5쪽의 `pages` 레코드를 읽는다. 쪽당 12KB 안팎이라 가볍고, `stream` 에 두어 같은 쪽을 다시 읽지 않는다.
- **미추출 쪽에서 끊긴 청크는 작다**: 추출 큐가 ±5쪽을 먼저 처리하므로(9-4) 드물 것이다. 가져온 직후 첫 낭독에서 호출당 평균이 낮게 나올 수 있다. 16-D4 의 "≥ 4,000자" 는 그래서 **연속 20,000자 낭독 뒤** 기준이다.
- **"오늘 상한까지 약 n쪽"** 은 `readStats` 가 5쪽 이상 쌓이기 전까지 숨는다. 한 책 안에서도 쪽 밀도가 들쭉날쭉하면(표·그림 쪽) 오차가 난다. 이 값은 추정 표시일 뿐이다.
- **이미지 표(CMDT 2021)**: 리플로우만 보면 표가 있는 줄 모른다(캡션만 남는다). 표본 쪽의 24.5% 에 이미지가 있다. 이번 범위에서는 대응하지 않고 기록만 했다. 사용자가 이 책을 리플로우로 읽기 시작하면 가장 먼저 부딪힐 결함이다.
