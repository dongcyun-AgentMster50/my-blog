## 1. 왜 30쪽이 그렇게 읽히나
- CMDT 2026 21–38쪽은 세 열 표다: 주제(여러 줄, 행 안에서 세로 가운데) | 참조 쪽 번호(소행마다) | 내용(글머리 + 인용).
- 4-5 는 거터를 하나만 고른다. 쪽마다 주제·쪽 번호 사이(8쪽)나 쪽 번호·내용 사이(10쪽)로 갈린다. 그래서 숫자가 내용 줄에 붙거나("ankle 1654 arthritis") 주제 줄에 붙는다("& Pseudo- 1130"). 읽기 순서도 왼쪽 단 전부 → 오른쪽 단 전부다.
- 4-7: 주제 줄은 글자가 커서 줄마다 heading 이 되고, 4-9 가 그 줄마다 문단을 끊는다. 18쪽에서 heading 문단이 342개다. 실제 주제 칸은 116개이고 그중 59개가 여러 줄이다.
- 4-8 은 조밀한 격자를 찾는 규칙이라 표를 0개 잡는다. 후보 조건은 body 역할, run 2개 이상, 이웃 후보가 2.2×Lm 이내다. 이 표의 주제 줄은 heading 이고, 숫자 줄은 4~6줄 간격으로 떨어져 있다.
- 규모(18쪽, 단위 1,006개): 쪽 번호 조각이 157개다. 쪽 번호만인 단위가 63개, 쪽 번호가 끼어든 문장이 약 98개다.

## 3. 설계 요약 (spec 4-13)
- **7b 단계** `js/text/rowtable.js`(순수)를 4-7 다음, 4-8 앞에 둔다. 띠는 폭 > 0.55W 인 줄로 끊고, 빈 세로 통로로 열을 나눈다. 열은 셋으로 가른다: 산문 열 P, 짧고 드문 이름표 열 A, 전부 정수인 열 R. 행 동기를 보고, 다른 글 열이 있으면 제외하고, 번호 이름표 가드를 둔다. 책 고유 x·글자 크기·낱말은 쓰지 않는다.
- **R7 물려받기(보완 2026-10-13)**: 행 표로 판정된 띠와 이웃한(가로지르는 줄로만 갈린) 띠는 그 열 경계로 다시 나눈다. 다음을 모두 만족하면 같은 표의 행으로 본다.
  - 조각이 모두 A·R·P 영역 안이거나 구획 행이다.
  - A 조각과 P 조각이 있다.
  - R 영역은 정수뿐이다.
  - 짧은 이름표 칸이 하나 이상 있다.
  - 가로지름이 띠 줄의 30% 이하다.
  같은 쪽 안에서만, 연쇄로 물려준다. 장 제목 사이의 한 행짜리 띠가 R3 의 "P 줄 ≥ 5" 를 못 넘어 빠지던 것을 살린다. 21–38쪽 131행 중 15행(11%)이 빠져 있었다: 21쪽 3, 22쪽 2, 29쪽 7, 30쪽 2, 31쪽 1. 30쪽은 Thyroid … Hirsutism 6행 전부가 잡힌다.
- **행 나누기**: 열마다 칸으로 묶는다(간격 > 1.4×행간). 구획 행은 단단한 경계로 둔다. P 글이 없는 이름표는 홀로 선 행이다. 닻(A 칸 ↔ 겹치는 P 칸) 사이 칸은 표마다 정렬을 골라 배정한다. 위 정렬이면 앞 닻에 붙이고, 가운데 정렬이면 DP 로 나눈다. 괘선(연산자 목록)은 dev 채점에만 쓴다.
- **결과 모양**: 띠의 줄을 열별 줄로 다시 만들어 행 순서로 끼우고 id 를 다시 매긴다. A 칸은 문단 정확히 하나(kind **rowhead**, 하이픈 결합)이고, P 칸은 칸 안에서만 4-9 로 나눈다. R 줄은 role **ref**(흐름 밖)다. 열 머리 행은 **colhead**(접힘)다. 저장본에는 줄 `rt`, 문단 `refLineIds` 를 더한다.
- **낭독**: `buildUnits` 는 바꾸지 않는다. 행마다 주제 한 단위 → 내용 문장 → 다음 행 순서다. 8h 인용 판별은 그대로다.
- **화면**: rowhead 는 굵게, 행 구분선을 둔다. 쪽 번호는 주제 끝에 작은 회색 숫자로 보이고(`.line` 아님) 낭독·하이라이트는 없다. 원본 보기는 바꿀 것이 없다. 줄을 쪼갠 덕에 주제와 쪽 번호를 함께 덮던 상자도 없어진다.
- **영향**: algoVersion 10 → 11 로 모든 책을 재추출한다. 데스크톱 실측은 CMDT 2021 5,051쪽 36초, CMDT 2026 31초, Harrison 9초다. 폰은 3–5배로 보고 5,000쪽에 약 2–3분으로 추정한다. 번역 캐시 키는 21–38쪽에서만 바뀐다(새 번역 약 230문장). 잡히지 않은 쪽은 바이트 단위로 같아야 한다(Review 기준). 8g 는 아직 Build 전이고, rowhead 가 heading 이 아니므로 목차 폴백에 섞이지 않는다.

## 5. Build 나누기
- **Build 는 하나(8i)**다. 순수 계층만 따로 배포하면 옛 `describePage` 가 ref 줄을 읽는다.
- 순서: ① `rowtable.js` + `config.ROWTABLE`(ENABLED 포함) + 단위 테스트 → ② `layout.js`(7b, id 재부여, algoVersion 11)·`blocks.js`·`store.js` → ③ `reader.js`·CSS → ④ `dev/measure-rowtable-8i.mjs`(앱 모듈로 세 권 수치, 괘선 대조, 쪽 번호 칸 전수, 잡히지 않은 쪽 바이트 비교) + import map 도장.
- 테스트 RT1–RT15(RT14 한 행짜리 띠, RT15 표 아래 2단 산문은 물려받지 않음), 변이 M1–M12(M11 R7 제거 → RT14, M12 가로지름 상한 제거 → RT15)는 spec 4-13-8 에 있다.
- 되돌림: `ROWTABLE.ENABLED=false` 와 함께 algoVersion 을 12 로 올린다(버전은 앞으로만).
- 이번엔 못 함: 연속 쪽으로 물려주기(21–38쪽은 쪽마다 직접 잡히는 띠가 있어 필요 없다), 두 줄로 넘어간 장 제목의 둘째 줄("TURNER SYNDROME"·"IN CARDIOLOGY")이 이름표로 들어가는 흠(손실은 없다), 목차 쪽(6–7), 2단 쪽 한 단 안의 행 표, 일반 다열 표의 부분 감지(4-8 문제), 이름표를 다시 찍지 않는 쪽 넘김 행, 숫자 격자 미검출.

## 6. 곁가지 관찰 (조치 없음)
- 측정 도구 `measure-lib.pageLayout` 은 이웃 쪽을 넘기지 않는다. 그래서 짝수 쪽 머리말 일부(93쪽)가 heading 으로 남는다. 앱은 이웃을 넘기므로(쪽 번호 진행 신호) 실제로는 header 로 잡힐 가능성이 높다. **앱에서 확인하지는 않았다.** 이 도구로 머리말 관련 수치를 잴 때는 부풀어 나온다는 점만 적어 둔다.
