# Plan 지침 — MedReader (의학 원서 리더 학습 웹앱)

## 너의 역할

이 프로젝트의 **Plan 단계** 담당이다. MedReader 웹앱의 설계 문서(`spec.md`)를 작성한다.

**구현하지 않는다.** 코드를 한 줄도 쓰지 마라. 오직 설계 문서 한 개만 만든다.

## 수정 허용 범위

**오직 이 파일 하나만 생성한다.**

```
/home/user/my-blog/apps/medreader/spec.md
```

다른 어떤 파일도 만들거나 고치지 마라. 블로그의 기존 파일(`index.html`, `css/`, `js/`, `posts/`, `apps/2048/`)은 읽는 것은 되지만 절대 수정하지 마라. 루트의 빈 파일 `.nojekyll`은 건드리지 마라.

## 프로젝트 배경

`/home/user/my-blog`는 마크다운 블로그 + 미니 웹앱 포트폴리오다(GitHub Pages 정적 호스팅). 만든 웹앱은 나중에 블로그 메인 페이지에 카드로 임베드된다.

먼저 읽을 것:
- `/home/user/my-blog/CLAUDE.md` — 프로젝트 규칙
- `/home/user/my-blog/apps/2048/spec.md` — 이 레포의 spec 문서 관례(형식·깊이·톤). 이 수준 이상으로 구체적이어야 한다. 다만 MedReader는 훨씬 큰 앱이므로 분량이 2~4배 될 수 있다.

지켜야 할 프로젝트 규칙:
- 웹앱은 `/apps/medreader/` 폴더 안에 **자체 완결**된다. 바깥 파일에 의존하지 않는다.
- 프레임워크·번들러 없이 순수 HTML, CSS, JavaScript + ES modules. 빌드 단계 없음.
- 외부 라이브러리 최소화. **웹앱에서는 CDN 허용**(pdf.js 등). 블로그 본체는 CDN 금지지만 그건 우리 범위 밖.
- 모바일에서도 사용할 수 있어야 한다 — 이 앱은 **모바일이 주 환경**이다.

### 🔴 실측에서 나온 기술적 제약 (spec에 반드시 반영)

**1. 폰트가 서브셋 CID 인코딩 (Type0)**
각 폰트가 독자적 글리프 번호 체계를 씀. ToUnicode를 폰트별로 해석해야 함.
전역으로 합치면 글자가 뒤섞임(실측: Choose→whoose, Clinical→wlinical).
→ **반드시 pdf.js의 getTextContent()를 사용할 것. 직접 파싱 금지.**

**2. PDF 텍스트 스트림에 줄바꿈 정보가 없음 ★최중요★**
추출 원문이 "poses the leastcardiovascular risk"처럼 붙어 나옴.
그런데 이 앱의 1순위 기능이 "읽는 줄을 강조 표시"임.
→ pdf.js textContent items의 transform 행렬에서 **Y좌표로 줄을 재구성**해야 함.
→ 각 줄의 bounding box를 계산해 하이라이트 오버레이를 그리는 구조로 설계.
→ 줄 재구성 알고리즘(Y 허용오차, 다단 컬럼 판별, 읽기 순서)을 spec에 명시.
→ 구현 난이도 최상. 별도 모듈로 분리하고 수용 기준을 따로 둘 것.
→ Phase 1 착수 시 이 모듈만 먼저 프로토타입으로 검증하고 나머지를 붙일 것.

**3. 표는 열 경계가 소실됨**
실측: "Acetylsalicylic acid650 POq4h" 처럼 붙음.
→ 표 영역 감지 시 폴백: 해당 페이지 영역을 canvas 렌더 이미지로 함께 표시,
   또는 AI에 재구성 요청. 표를 그냥 낭독하면 의미 없는 소리가 남.

**4. 이 책은 "객관식 문제 + 해설집"이다 ★설계 반영★**
실제 구조:
  "Choose the one best response to each question"
  "1. Which of the following can help reduce errors in the delivery of health care?
    A. Checklists to ensure important steps are not forgotten
    B. Clinician honor code ..."
사용자의 연말 대학원 시험 대비 자료와 정확히 일치.
→ 문제/보기/정답/해설 구조를 파싱해 퀴즈 모드를 제공.
→ 단, 구조 판별은 실패할 수 있으므로 일반 리더 모드가 항상 기본이고
   퀴즈 모드는 감지 성공 시 제안하는 방식으로.

**5. 저장 용량**
729p / 25MB → IndexedDB에 통째로 저장 가능. 챕터 분할 불필요.

### 🔴 평가 기능 설계 원칙 (spec에 반드시 반영)

**A. 문항 출처를 반드시 구분해 표시할 것**
  📕 원서 문제  = PDF에서 추출한 검증된 문항
  🤖 AI 생성 문제 = 읽은 본문으로 AI가 출제한 문항
두 종류를 섞어 표시하지 말 것. 배지로 명확히 구분.
AI가 틀린 의학 문항을 내고 사용자가 그걸 외우면 실제 시험에서 손해를 봄.

**B. AI 출제는 grounding 필수**
- **사용자가 실제로 읽은 원문 범위 안에서만 출제.** 원문 밖 의학 지식 사용 금지.
- 각 AI 문항은 **근거가 된 원문 문장을 함께 저장·표시**할 것.
- 근거 문장을 제시하지 못하는 문항은 버릴 것(생성 후 자체 검증 단계를 둘 것).
- 해설은 아랍어 + 영어 병기.

**C. 어학 4기능 테스트 (en / ko / fr)**
- 읽기: AI 생성 지문 + 문항
- 듣기: TTS로 지문 낭독 + 문항 (실제 시험 음성은 저작권상 사용 불가)
- 쓰기: 작문 → AI 채점 + 첨삭
- 말하기: Web Speech 음성인식 → 전사 → AI 채점
  ⚠️ 발음 정확도 평가는 브라우저 API로 한계가 있음.
     내용·유창성·문법 위주로 채점하고, 발음은 참고 수준임을 UI에 명시.
- TOEFL/TOPIK/DELF 실제 기출문제는 저작권상 앱에 포함 금지. AI 생성 유사문항만.

**D. ★점수 신뢰도 고지 (필수)★**
앱이 산출하는 TOEFL/TOPIK/DELF 환산 점수는 검증되지 않은 자체 추정치임.
사용자가 이를 실제 점수로 오인하면 장학금 준비에 직접적 피해가 감.
→ 점수 표시 옆에 항상 "참고용 추정치 · 공식 모의고사로 검증 필요" 고지.
→ ETS / TOPIK(국립국제교육원) / France Éducation International의
   공식 무료 샘플 링크를 결과 화면에 함께 배치.

### 💰 비용 제로 설계 (사용자가 돈을 내지 않는 것이 요구사항)

**원칙: AI 호출은 최후 수단**
다음 기능은 API를 절대 호출하지 말 것 (전부 로컬/무료):
  TTS 낭독, 줄 하이라이트, 스크롤, PDF 렌더·검색·페이지 이동,
  글자 크기·테마·리플로우, 원서 문제(📕) 풀이, 플래시카드 복습,
  음성 인식, 캐시된 번역·요약 재열람,
  ICD-11 / PubMed / Europe PMC / openFDA (무료 공개 API)

API가 필요한 기능은 4개뿐: 번역 · 요약 · AI 출제(🤖) · 작문 채점
사용자의 1순위 요구(낭독 + 하이라이트)는 전부 무료·오프라인 영역에 있어야 함.

**호출 절감 (spec에 구현 방식까지 명시)**
1. 캐싱 — 번역·요약 결과를 IndexedDB에 (문서ID + 텍스트해시) 키로 저장.
   재방문 시 API 호출 0회. 캐시 적중률을 사용량 대시보드에 표시.
2. 요청 병합 — 문단 단위가 아니라 페이지(또는 N문단) 단위로 묶어 1회 호출.
3. 지연 호출 — 자동 전체 번역 금지. 사용자가 탭한 줄/문단만 호출.
4. 온디바이스 우선 — Chrome 내장 Translator / Summarizer / Language Detector API를
   기능 감지(feature detection)해서 사용 가능하면 우선 사용, 없으면 원격 API로 폴백.
   Android Chrome 지원이 불안정하므로 반드시 폴백 경로를 먼저 완성할 것.
   이 기능 유무로 앱이 깨지지 않을 것.
5. 모델 선택 — 기본값은 가장 저렴·경량인 Flash 계열. 설정에서 변경 가능.
6. 사용량 대시보드 — 오늘/이번 달 호출 수와 캐시 절약분을 앱에 표시.
   일일 상한을 사용자가 직접 설정할 수 있게 하고, 임박 시 경고 후 차단.
   무료 티어 한도 수치를 코드에 하드코딩하지 말 것(정책이 자주 바뀜).

**한도 초과 시 UX**
무료 티어 초과는 과금이 아니라 차단(429)임. 이를 명확히 안내할 것:
  "오늘 무료 한도에 도달했습니다. 낭독·읽기·복습은 계속 사용할 수 있고,
   번역은 내일 다시 가능합니다."
→ 429를 에러가 아닌 정상 상태로 처리. 앱이 죽거나 무한 재시도하지 말 것.
→ 오프라인 가능 기능으로 자연스럽게 유도.

**서버 프록시는 만들지 않음 (현 단계)**
개발자 계정 키를 서버에 두는 프록시 방식은 Phase 1 범위에서 제외.
실제 사용량 측정 후 재검토. 프로바이더 추상화 계층만 만들어 두어
나중에 백엔드 엔드포인트를 추가해도 앱 코드 변경이 최소가 되게 할 것.

### 🔒 프라이버시 가드레일 (필수)
사용자는 현직 레지던트이며, 무료 API 티어는 입력이 모델 개선에
사용될 수 있음(해당 지역은 옵트아웃 대상이 아님).

### Phase 1 — 리더 핵심 (spec.md는 이 범위를 상세히)
1. PDF 열기 — pdf.js(CDN 허용) + getTextContent() 기반 텍스트 추출
2. 줄 재구성 엔진 — 좌표 기반 라인 그룹핑 + bounding box (제약 2)
3. 줄 단위 TTS 낭독(Web Speech API) + 현재 줄 하이라이트 + 속도 조절
   + 일시정지 / 이전 줄 / 다음 줄, 낭독 중 화면 자동 스크롤
4. 줄 탭 → 아랍어 즉시 번역 (인라인 표시)
5. 문단 끝 → AI 요약 (아랍어 + 영어 병기)
6. 눈 피로 대응 — 글자 크기/줄간격/자간 조절, 다크·세피아 모드, 고대비,
   리플로우 텍스트 뷰(원본 레이아웃 무시하고 큰 글씨로 다시 흘리기)
7. 모바일 우선 UI — 한 손 조작, 큰 터치 타깃, 하단 컨트롤 바
8. 아랍어 RTL 기본 + 4개 언어 UI (ar/en/fr/ko), CSS 논리적 속성만 사용
9. BYOK — 프로바이더 추상화 (Gemini 기본 / Mistral·OpenRouter·Claude·OpenAI 교체 가능)
10. 퀴즈 모드 — 원서 문제 추출 후 풀이 (📕 배지)
11. 사용량 대시보드 + 일일 상한 설정 + 캐시

### Phase 2 — 서재 + 평가 루프
12. PDF 서재: 앱 내 저장·검색·색인
13. ICD-11 챕터 기반 질병·전공별 자동 분류 (4개 언어 공식 병명)
14. 진도 추적 — 섹션 단위 읽기 완료 기록
15. **섹션 종합 복습 테스트** — 원서 문제 + AI 생성 문제 혼합 출제 (평가 원칙 A·B 적용)
16. 오답 노트 + 용어 SRS 카드 (SM-2)
17. 필기 / 하이라이트 저장 (페이지 앵커)

### 제약 및 가드레일 (spec에 명시)
- 정적 사이트(GitHub Pages). 백엔드 없음. 순수 HTML/CSS/JS + ES modules, 빌드 없음
- API 키는 sessionStorage 기본, "이 기기 기억" 선택 시에만 localStorage.
  로그·URL·에러 메시지에 절대 노출 금지
- 모든 사용자·AI 출력은 textContent 또는 sanitize 후 삽입 (XSS 차단)
- AI 응답 JSON은 방어적 파싱 — 깨진 응답에 앱이 죽지 않을 것
- 전 화면 고정 고지: "교육 목적. 임상 의사결정에 사용 금지"
- AI가 치료 프로토콜을 생성하지 않음.
  임상 사실은 ICD-11 / PubMed / Europe PMC 실데이터와 UpToDate 딥링크가 담당
- UpToDate·VisualDx 등 유료 DB는 스크래핑·재요약 절대 금지. 딥링크만
- 의료 영상 AI 판독 기능 없음. 교육용 참조 이미지 검색까지만
- 아랍어 TTS 음성 팩이 기기에 없을 수 있음 → 감지 후 설치 안내 UI 필요
- 오프라인/네트워크 실패 시 UX 정의 (읽기·낭독·복습은 오프라인 동작, 번역·출제만 온라인)
- ⚠️ 사용자의 PDF를 레포에 절대 커밋하지 말 것. 공개 저장소이고 저작권 자료임. 파일은 사용자 기기에만 저장
- 루트의 빈 파일 .nojekyll 을 지우거나 건드리지 말 것

## spec.md에 반드시 포함할 섹션 (사용자가 명시한 목록)

1. **요약** — 문서 맨 위 한 문단으로 "무엇을 만드는지".
2. **파일 구조** — `/apps/medreader/` 안의 모든 파일과 각 모듈의 책임. ES modules 기준. pdf.js CDN 로딩 방식(버전 고정, worker 경로, 실패 시 UX) 포함. Phase 1 파일과 Phase 2·3에서 추가될 파일을 구분.
3. **각 모듈 책임** — 모듈 간 의존 방향(누가 누구를 import하는지). 규칙/알고리즘 계층은 DOM을 모르게(2048 spec의 "규칙 계층이 DOM을 모른다" 원칙과 같은 취지).
4. **줄 재구성 알고리즘 상세** ★가장 중요★ — pdf.js `getTextContent()` items의 `transform`(6-tuple), `width`, `height`, `hasEOL`, `fontName`을 어떻게 쓰는지. 구체적으로:
   - Y 허용오차(폰트 크기 비례 vs 고정값) 결정과 근거
   - 아이템을 줄로 묶는 절차(정렬 → 클러스터링 → 줄 내 X 정렬 → 아이템 사이 공백 삽입 규칙: X 간격이 폰트 크기의 몇 배 이상이면 공백)
   - 다단 컬럼 판별(X 히스토그램 / 갭 탐지 등) 과 읽기 순서(컬럼 우선 → 위에서 아래)
   - 페이지 헤더·푸터·페이지 번호 제외 휴리스틱
   - 줄 → 문단 그룹핑(줄 간격 급증, 들여쓰기, 문장 종결 부호)
   - 하이픈 줄바꿈 결합("cardio-" + "vascular")
   - 줄 bounding box 계산과 PDF 좌표 → 뷰포트(canvas/CSS px) 변환, 하이라이트 오버레이 구조
   - 표 영역 감지 휴리스틱(짧은 아이템이 같은 Y에 여러 개 + 큰 X 간격 반복)과 폴백(canvas 크롭 이미지 표시 / AI 재구성 버튼)
   - 이 모듈만의 **별도 수용 기준** 과 프로토타입 검증 절차(Phase 1 착수 시 이 모듈을 먼저 검증)
   - 실측 예시("poses the leastcardiovascular risk", "Acetylsalicylic acid650 POq4h", "Choose→whoose")를 테스트 케이스로 명시
5. **문제/보기/정답/해설 구조 파서** — Harrison's Self-Assessment 형식(문항 번호 + 보기 A~E + 정답/해설 섹션) 감지 규칙, 감지 실패 시 리더 모드 유지, 감지 성공 시 퀴즈 모드 제안 UX. 정답 매칭이 불확실한 문항은 📕 배지를 주지 않고 "정답 미확인"으로 표시.
6. **TTS·하이라이트·자동 스크롤** — Web Speech API 사용 방식. **Android Chrome에서의 Web Speech API 제약과 폴백** 을 별도 소절로:
   - `onboundary` 이벤트가 Android Chrome에서 안 오는 문제 → 줄 단위 `onend` 체이닝으로 대응
   - 긴 utterance가 잘리는 문제(약 15초/200자 이슈) → 줄 단위로 짧게 끊음
   - `getVoices()`가 비동기·초기 빈 배열 → `voiceschanged` 대기
   - 백그라운드/화면 꺼짐 시 중단 → Wake Lock API 검토, 실패 시 안내
   - 아랍어/한국어/프랑스어 음성 없음 감지 → 설치 안내(설정 > 언어 및 입력 > TTS 출력)
   - `speechSynthesis.pause()` 버그(Android) → cancel + 현재 줄부터 재개로 구현
   - 음성인식(SpeechRecognition)은 Android Chrome에서 네트워크 필요·Web Speech 미지원 브라우저 폴백
7. **번역·요약 파이프라인** — 온디바이스 API(feature detection: `'Translator' in self`, `'Summarizer' in self`, `'LanguageDetector' in self`) 우선 → 원격 폴백. 요청 병합 단위, 지연 호출, 캐시 키(문서ID + 텍스트 SHA-256 해시 + 대상언어 + 작업종류), 429 처리 상태 기계.
8. **프로바이더 추상화 인터페이스** — `AIProvider` 인터페이스(예: `translate(segments, targetLang)`, `summarize(text, langs)`, `generateQuiz(passage, n)`, `gradeWriting(text, rubric)`, `verifyKey()`, `estimateTokens()`)와 어댑터(Gemini 기본, OpenAI 호환, Anthropic, Mistral, OpenRouter). 나중에 서버 프록시(`ProxyProvider`)를 끼울 수 있도록 어댑터가 `{endpoint, headers, bodyBuilder, responseParser}` 형태로 분리. 키 검증은 형식 정규식(구형 `AIza...`·신형 `AQ....` 모두 허용) + 실제 호출 1회. CORS 관점에서 브라우저에서 직접 호출 가능한 프로바이더와 불가능한 프로바이더(Anthropic은 `anthropic-dangerous-direct-browser-access` 헤더 필요)를 표로 정리.
9. **IndexedDB 스키마** — 스토어: 문서(documents: PDF blob + 메타), 페이지 텍스트 캐시(pages: 줄/문단 구조), 진도(progress), 문항(questions: source 📕/🤖, grounding 문장, 정답), 시험 결과(attempts), 오답(mistakes), 카드(cards: SM-2 필드), AI 캐시(aiCache), 사용량(usage: 일별 카운트), 설정(settings), 필기(annotations). 각 스토어의 키·인덱스·필드·버전 마이그레이션 정책. Phase 1에 필요한 스토어와 나중 스토어를 구분하되 스키마는 처음부터 전부 정의(버전 1에 다 만들지, 버전 증가로 추가할지 판단).
10. **AI 프롬프트 설계** — 번역·요약·출제·채점 4종의 시스템 프롬프트 골격과 JSON 응답 스키마, 방어적 파싱 규칙(코드펜스 제거, 부분 JSON 복구, 스키마 검증 실패 시 UX). 출제 프롬프트는 grounding 규칙(원문 밖 지식 금지, 근거 문장 인용 필수)과 생성 후 자체 검증(근거 문장이 실제 원문에 부분 문자열로 존재하는지 로컬 검사) 포함. 치료 프로토콜 생성 금지 지시 포함. 프롬프트 인젝션(PDF 본문에 지시문이 들어 있을 수 있음) 대응.
11. **i18n 키 구조** — 4개 언어(ar/en/fr/ko), 키 네이밍 규칙, 파일 형식(JS 모듈 vs JSON — 빌드 없음·file:// 고려), RTL 처리(`dir` 속성, CSS 논리적 속성만), 언어 감지 초기값, 폰트(아랍어 가독성).
12. **화면 구성과 UX** — 모바일 우선. 화면 목록(온보딩/프라이버시 동의, 서재, 리더, 퀴즈, 설정, 사용량), 리더의 하단 컨트롤 바(재생/일시정지/이전/다음/속도), 줄 탭 → 번역 인라인, 문단 끝 요약 버튼, 리플로우 뷰 vs 원본 뷰 전환, 눈 피로 설정, 큰 터치 타깃(최소 44~48px). 전 화면 고정 고지 위치.
13. **프라이버시·보안** — 키 저장 정책, 로그·에러 메시지 마스킹 규칙, XSS(textContent/sanitize), 개인정보 패턴 경고(확인 후 진행), 최초 실행 동의, PDF는 기기에만.
14. **오프라인/네트워크 실패 UX** — 기능별 온/오프라인 매트릭스, 429·네트워크 오류 메시지, 무한 재시도 금지.
15. **사용량 대시보드와 상한** — 계산 방식, 저장 위치, 상한 임박 경고·차단, 한도 수치 하드코딩 금지.
16. **Phase 1 수용 기준(acceptance criteria)** — Review 서브에이전트가 체크할 수 있는 형식. 줄 재구성 모듈은 별도 항목. 실기기(Android Chrome) 확인 항목과 데스크톱에서 확인 가능한 항목을 구분.
17. **Phase 2·3 개요** — 상세 설계는 하지 말고, Phase 1 설계가 나중 단계를 막지 않도록 확장 포인트(스키마·모듈 경계)만 명시.
18. **미결정 사항과 판단** — 정답이 없는 것들은 네가 판단하고 이유를 적어라(아래 참고).

## 판단해서 정할 것

- 리더 기본 뷰를 원본 canvas 뷰로 할지 리플로우 텍스트 뷰로 할지(눈 피로가 핵심 문제이고 모바일이므로 리플로우가 기본일 가능성이 높지만, 표·그림은 원본이 필요함)
- pdf.js 버전(안정 버전 고정)과 ESM 빌드(`pdf.min.mjs`) vs 레거시 빌드 선택, worker 로딩 방식
- 텍스트 해시 함수(`crypto.subtle.digest` — https/localhost에서만 동작, file://에서는 폴백 필요)
- 요약 단위(문단 vs 페이지)와 자동 트리거 여부(자동 호출 금지 원칙과의 균형)
- 줄 하이라이트를 원본 뷰에서 오버레이로 그릴지, 리플로우 뷰에서 DOM 요소 class 토글로 할지, 둘 다인지
- 대용량 PDF(25MB) 최초 로드 시 전체 페이지 텍스트를 미리 추출할지(진행 표시 필요) vs 열람 페이지만 지연 추출할지
- 온보딩 흐름 길이(키 입력을 첫 화면에서 강제할지, 키 없이도 낭독/읽기는 되게 할지 — 비용 제로 원칙상 키 없이도 되어야 함)

## 문서 형식

한국어로 작성한다. 전문용어는 영어 병기. 구현자(Build 서브에이전트)가 이 문서만 읽고 바로 만들 수 있을 만큼 구체적이어야 한다. 알고리즘은 말과 의사코드로 설명하고, 실제 코드는 쓰지 마라(인터페이스 시그니처·JSON 스키마·의사코드는 허용). 표를 적극 활용하라.

분량 목표: 1,200~2,000줄. 줄 재구성 알고리즘(4번)과 Phase 1 수용 기준(16번)이 가장 두꺼워야 한다.
