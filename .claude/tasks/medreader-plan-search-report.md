**쪽 라벨** — CMDT 2026 만 있다. 1,967쪽 전부 PDF 쪽과 다르고 본문 1,704쪽은 **인쇄 쪽 = PDF 쪽 − 38**.

**heading** — 1,017 / 12,670 / 5,997개. 반복 소제목(같은 글자 10번 이상)이 32%(CMDT 2026)·61%(CMDT 2021). 소제목 글자 크기 층이 책마다 다르다(CMDT 2026 1.15~1.4배 6,035개, CMDT 2021 1.4~1.8배 5,348개) → 트리 목차로 못 쓴다. 대신 검색어가 든 heading 은 0~66개(예: "sarcoidosis" 3개 대 본문 적중 66쪽) → 결과 첫 묶음 "제목"으로 쓴다.

## 3. 검색 방식 권장안과 근거

**(i-b) 쪽별 검색 글자 스토어 `searchText`(DB 버전 3) + 열린 책 메모리 캐시.**
- 목표(Realme GT7T): 한 책 첫 검색 ≤ 1초, 다음 검색 ≤ 150ms, 서재 전체 ≤ 3초. 목표 밖은 (i) 하나뿐이고, (i) 의 비용은 검색에 필요 없는 좌표를 푸는 데서 온다 — 글자만 따로 두면 1/9.
- 쪽 단위라 **추출이 덜 끝난 책이 저절로 처리된다**(있는 쪽만 찾고 "n쪽 중 m쪽" 표시). `pages` 와 한 트랜잭션에 쓰니 `algoVersion` 경첩을 그대로 탄다. 원문을 저장하고 접기는 읽을 때 하므로, 접기 규칙을 고쳐도 다시 만들 필요가 없다. 레코드 모양이 바뀌면 `SEARCH_VERSION` 하나로 백필이 다시 만든다(재추출 없음).
- 이미 추출된 책(Nour 기기)은 검색을 처음 열 때 `pages` 에서 **백필**(책마다 한 번, 폰 3~5초 `[추정]`, 진행 표시).
- 역색인(ii)은 비채택: 권당 1,000만 자에서 훑기가 이미 5ms 라 이득이 없고, 구·접두 확인에 쪽을 다시 읽어야 하며, 추출 중 쓰기가 폭증한다. gzip 덩어리(iii)는 **폰 실측이 목표를 넘을 때의 대안**으로 남긴다.
- 정규화는 최소: 길이 보존 1:1 접기(소문자·하이픈/대시 → 공백·악센트·따옴표) + 검색어 변형(β↔beta 등 그리스 문자 5개) + 2~5자 대문자 약어는 대소문자 구분 낱말 일치 + 4자 이상은 낱말 시작 접두 일치. 어간·철자 교정·동의어 없음.
- 목차는 **PDF 개요**(세 책 100%), 개요가 없는 책만 heading 상위 크기 층 폴백. 퀴즈 섹션 색인(5절)은 문항 섹션만 담아 재사용하지 않는다.
- **AI 호출 0.** 아랍어 검색어는 안내만(기본). 선택지: 8f 단어장 대응(호출 0), 번역 캐시에서 찾기(호출 0, 기록만), AI 번역 버튼(기본 끔).

## 4. 화면 요지

- 진입: 리더 상단바 **[🔍]**(이 책) · 서재 상단 **[검색]**(서재 전체). 화면 = 범위 전환 · 검색 칸(`dir=auto`) · 탭 **[찾기] [목차]** · 결과(묶음 순서 제목 → 본문 → 표, 쪽당 한 줄 "p. 170 (PDF 208) · 3곳 · 조각").
- 결과를 누르면 그 쪽으로 가서 쪽의 적중 전부를 `search-hit`, 고른 것을 `search-cur` 로 칠한다(`charhl` 재사용, 낭독 하이라이트와 **이름이 달라 서로 지우지 않는다**) → 화면 가운데로 스크롤. 줄바꿈 하이픈을 넘는 적중은 `joinPieces` 의 `spans` 로 두 줄에 나눠 칠한다. 표 적중은 표 블록으로, 원본 뷰는 줄 오버레이로.
- 리더 위 **검색 띠** `"검색어" ‹ n/m › [읽던 곳으로] ✕`. Android 뒤로 = 결과 목록.
- **낭독 중 결과로 가면 멈춘다**(결정) — 적중 문장이 다음 [▶] 의 시작점. 이어 읽으면 낭독 동반 번역이 새 위치에서 냉시작 요청을 바로 보내 한도를 쓰기 때문이다. [읽던 곳으로]가 원래 위치로 돌려보낸다.
- 아랍어 UI: 화면은 RTL, 조각·개요 제목은 `dir=ltr lang={문서 언어}` 블록, `<mark>` 포함 전부 `textContent`. 검색어를 되풀이하는 문구만 `bididom` 으로 격리. 48px.
- 키보드 없이: 목차 탭은 타이핑 없음, 검색 칸은 휴대폰 키보드 음성 입력 `[가정]`, 최근 검색어 칩 5개. 9b 음성 명령의 "찾기 …"(자유 낱말)는 9b 설계 때 본다(언급만).

## 5. 로드맵 배치 권장

**배포 안전장치 → Nour 공개 → 8g 검색 → 8d → 8e → 9a …** (19-1 에 "운영자 결정 대기"로 적음)
- 공개 전 필수로 넣지 않는다: 공개 전 묶음은 커밋됐고 배포 결정만 남았다. 그리고 **8g 는 DB 버전을 3 으로 올리므로 배포 안전장치 뒤에만 배포할 수 있다** — 옛 `db.js` 가 남은 탭은 `VersionError` 로 부팅하지 못한다.
- 8d 보다 앞: 8d 는 "Nour 가 띠를 써 본 반응을 보고 세부를 정한다"고 되어 있어 그 반응을 기다리는 동안 8g 를 한다. 지금은 5,051쪽에서 장을 찾아갈 수단이 없고, 호출 0·오프라인이다. 단 Nour 가 띠를 보고도 "아래에"를 다시 원하면 8d 를 먼저 한다.
- 나눌 수 있다: **8g-1 목차·인쇄 쪽 번호 표시**(DB 무관·작음 — 원하면 공개 전 묶음에도 붙일 수 있다) / **8g-2 키워드·제목 검색**(DB 3).

## 6. 사용자에게 물을 것

1. **8g 의 자리** — 권장: Nour 공개 직후, 8d 앞(띠 반응을 기다리는 동안). 대안: 8g-1(목차·인쇄 쪽 번호)만 공개 전 묶음에 붙이고 8g-2 는 공개 뒤.
2. **DB 버전 3 은 배포 안전장치 뒤에만 배포** — 권장: 지금 진행 중인 안전장치(작업 트리에 import map 도장·`resetDerived` 가 보인다)를 먼저 넣고, 8g Build 는 그 위에서. 안전장치를 미루기로 하면 8g 는 8g-1 만 먼저 가능하다.

## 7. 위험

- **폰 속도는 추정이다**(데스크톱 ×4 `[가정]`). Nour 폰에서 `dev/search-bench.html` 을 먼저 돌려야 한다 — (i-b)가 1초를 넘으면 (iii) gzip 덩어리로 바꾼다(spec 17-8-2 에 대안으로 둠). 벤치는 지어낸 글자라 실제 글자의 압축률과 다를 수 있다(쪽당 크기는 실측과 맞춤 — 1쪽 JSON 27.9 / 10.7KB 대 실측 31.3 / 10.0KB).
- **DB 버전 3 + 옛·새 모듈 혼재 = 부팅 실패**, 되돌릴 수 없다. 배포 안전장치 뒤에만.
- **백필 3~5초(폰, 책마다 한 번)** `[추정]` — 첫 검색이 그만큼 늦다. 진행 표시와 "이미 있는 쪽은 찾는다"로 완화.
- **열지 않은 책은 추출이 돌지 않는다** — 서재 전체 검색이 그 책의 일부만 찾는다. 결과 머리에 쪽 수와 [이 책 텍스트 준비 계속]을 둔다.
- **판 어긋남**(재추출 도중 등)이면 강조 위치를 못 찾을 수 있다 — 쪽 맨 위 + 한 줄 안내(틀린 강조보다 강조 없음).
- heading 목차 폴백은 실물로 검증되지 않았다(세 책 모두 개요가 있다) — 수용 기준에 개요를 지운 합성 문서로.
- **동시 작업**: 이 Plan 중 작업 트리에서 다른 Build(배포 안전장치 — `db.js` `DERIVED_STORES`·`resetDerived`, `dev/stamp-importmap.mjs`, `extract.js` `stopAndSettle` 등)가 진행 중이었다. 내 측정은 `js/text/*`·`tts/text.js` 만 거쳤고 그 파일들은 바뀌지 않았다(git diff 로 확인). spec 17-8-3·17-8-10 에 "`searchText` 를 `DERIVED_STORES` 에 더하고 import map 도장을 다시 찍는다"를 적었다 — 8g Build 지침에 옮길 것.
- 측정 중 쓴 임시 스크립트 두 개(`labels.mjs`·`heads.mjs`)는 스크래치패드에만 있다 — 같은 측정을 `dev/measure-search.mjs` 에 넣고 Harrison·CMDT 2026 으로 다시 돌려 같은 수치를 확인했다.
