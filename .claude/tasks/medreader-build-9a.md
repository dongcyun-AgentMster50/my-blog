# Build 지침 — MedReader 9a단계: 문항 파서 (`js/quiz/parser.js`, 순수 계층)

## 왜 이 단계가 중요한가

이 책은 **자가평가 문제집**이다. 퀴즈는 곁다리가 아니라 본체 기능에 가깝다.
그리고 파서는 **순수 계층**이라 브라우저 없이 전수 검증이 된다 — 여기서 정확도를 벌어라.

**곧 7000쪽 실제 자료로 교체된다**(형식 유사). 특정 서적 튜닝은 하지 마라.
아래 실측은 **규칙이 맞는지 확인하는 근거**지 맞춰야 할 목표 숫자가 아니다.

## 먼저 읽을 것

1. `apps/medreader/spec.md` — **5절 전체**(5-1 대상 형식 · 5-2 입출력 · **5-3 감지 규칙 ★** ·
   5-4 매칭과 상태). 5-3 앞의 `[실측 2026-09-24]` 표와 `[수정 2026-09-24 — 9a]`
   (`sectionId` 를 로마숫자로) 를 **반드시** 읽어라.
2. `apps/medreader/spec.md` 3-1·3-2(계층), 9절 `questions` 스토어 스키마
3. `.claude/tasks/medreader-handoff.md` — 환경·함정
4. 기존 자산: `js/text/segment.js`(`parseQuestionNumber`·`parseAnswerStart`·
   `isOptionStart` 등이 **이미 있다. 다시 만들지 마라**), `js/text/blocks.js`(문단 `kind`)

## 실측 (729쪽 전수 — 재측정 불필요, 근거로 쓰라고 주는 것이다)

```
question 문단 1,392   option 문단 6,264   answer 문단 1,187
보기 글자  A 1,272 / B 1,274 / C 1,272 / D 1,264 / E 1,182
문항↔정답 단순 매칭 1,181 (84.8%)      그림 참조 158     중복 문항 키 27
```

**로마숫자 그룹 I~X 는 깨끗하다.** 전부 1번부터 시작, 쪽 범위가 겹치지 않음,
건너뜀이 문항수 대비 아주 적음(V·VII·VIII 은 0). 이것이 사실상 섹션 경계를 공짜로 준다.

**로마숫자가 없는 101건은 거의 다 오탐이다.** 번호가 1~700 으로 흩어지고 되돌아감 28건.
표본: 57쪽에 1·2·3·4, 61쪽에 **다시** 1·2·3·4 — 쪽마다 1부터 다시 시작한다.
해설 본문 안의 번호 목록이다.

**`A.` 보기가 뒤따르지 않는 `question` 문단이 251개(18%)** 있다.

→ 오탐을 거르는 두 그물은 **번호 연속성**과 **보기 존재**다. 둘 다 5-3 에 이미 쓰여 있다.

## 만들 것

`apps/medreader/js/quiz/parser.js` — **순수 모듈 하나.**

```
parseSections(pageLayouts, opts) -> ParsedSection[]
```

- 입력은 `PageLayout[]`(추출된 연속 쪽 범위). 출력은 spec 5-2 의 `ParsedSection[]`.
- **문항 id 는 `"{docId}:{sectionId}:q{number}"`** 로 결정적이어야 한다(5-4).
  `docId` 는 `opts` 로 받아라 — 파서가 db 를 알면 안 된다.
- `sectionId` 는 **로마숫자 기반**(5-3 수정 2026-09-24). 쪽 범위로 만들지 마라.

### 반드시 지킬 것

- **순수 계층이다**(3-1). `document`·`window`·`fetch`·`indexedDB`·`navigator`·
  `localStorage` 를 **한 글자도** 쓰지 마라. Review 가 grep 으로 0건을 확인한다.
- **UI 문자열을 만들지 마라**(3-2). 코드·구조만 낸다. "정답 미확인" 같은 문구는 UI 몫이다.
- `js/text/segment.js` 의 기존 함수를 **재사용하라.** 정규식을 다시 쓰지 마라 —
  규칙이 두 벌이 되면 어긋난다(6a 에서 `lineBBox` 와 `extendRun` 이 그랬다).
- **파서가 던지면 리더가 죽으면 안 된다**(5-4 마지막 줄). 예외는 `stats.error` 로만 남기고
  그 섹션을 건너뛴다. 파서는 리더 렌더 경로 밖에서 돈다.
- **부분 추출을 견뎌라.** 7000쪽에서 문항은 추출됐는데 해설은 아직인 상태가 정상이다.
  그때 `status: 'unverified'` 이고, 나중에 재파싱하면 `verified` 로 승격돼야 한다(5-4).
- **중복 문항 키(실측 27건)** 를 어떻게 다룰지 5-4 가 정해 뒀다 — `unverified`.
  조용히 덮어쓰지 마라.

## 테스트

`node --test "apps/medreader/tests/*.test.mjs"` — **디렉터리 인자는 Node 24+Windows 에서 실패한다.**

파서는 순수하니 **전부 단위 테스트로 덮인다.** 최소한 이것들:

1. `I-1.` · `12.` 두 형태를 다 받는다.
2. **번호 연속성** — 7 다음 12 가 오면 보류하고 3문단까지 8 을 찾는다(5-3).
3. **보기 없는 문항 후보는 취소된다**(실측 251건이 여기로 걸린다).
4. 보기 글자가 A·B·C… 연속이어야 한다. `A, B, D` 처럼 건너뛰면 어떻게 되는가.
5. 정답 `The answer is B.` 와 복수 정답 `The answers are B and D.`
6. **정답 글자가 보기 범위 밖**(예: F) → `unverified`(5-4).
7. **중복 번호** → `unverified`. 조용히 덮어쓰지 않는다.
8. 해설이 아직 없는 문항 → `unverified`. **해설을 뒤에 붙여 재파싱하면 `verified` 로 승격.**
9. 로마숫자가 바뀌면 새 섹션. 번호가 1로 되돌아가도 새 섹션.
10. `sectionId` 와 문항 id 가 **결정적**이다 — 같은 입력에 같은 id.
11. 그림 참조 감지(`hasFigure`).
12. **문단이 페이지에 걸쳐 있어도** stem·보기·해설이 이어진다.
13. 파서가 던져도 호출자에게 예외가 새지 않는다(`stats.error`).

**변이 테스트**: 번호 연속성 검사와 보기 존재 검사를 각각 일부러 없앴을 때
**어떤 테스트가 빨개지는지** 확인하고 보고하라. 안 빨개지면 그 테스트는 헛돌고 있다.
(6단계 Review 에서 자기 이름의 규칙을 검증 못 하는 테스트가 실제로 나왔다.)

## 실물 PDF 검증 (필수)

오케스트레이터가 하네스를 만들어 뒀다. **경로는 프롬프트로 따로 준다.**
729쪽 전수로 `parseSections` 를 돌려 다음을 보고하라:

- 섹션 수와 각 섹션의 `{sectionId, questions, verified, unverified}`
- 전체 `verified / questions` 비율 — **5-4 의 0.6 임계를 넘는 섹션이 몇 개인가**
- **오탐이 실제로 걸러졌는가**: 로마숫자 없는 101건과 보기 없는 251건이
  최종 문항 목록에서 어떻게 됐는지 수치로
- 실행 시간과 최대 메모리 (7000쪽 환산도 함께)

**숫자를 실제 출력 그대로 붙여라.** 요약하지 마라.

## 완료 보고 형식 (한국어로)

1. 생성한 파일과 줄 수.
2. `node --test` **실제 출력**(tests/pass/fail).
3. 실물 PDF 전수 결과 — 위 4가지.
4. 변이 테스트 결과 — 무엇을 없앴고 무엇이 빨개졌는가.
5. **오탐 처리** — 로마숫자 없는 101건과 보기 없는 251건을 어떤 규칙이 걸렀는가.
   걸러지지 않은 것이 있으면 몇 건이고 왜인가.
6. spec 과 다르게 구현한 부분. 없으면 "없음".
7. `segment.js` 등 다른 모듈에서 발견한 버그 (**고치지 말고** 보고).
8. 7000쪽에서 걱정되는 것 3줄 이내.

**속도가 중요하다.** 테스트를 통과시키려고 spec 을 어기지 마라. 막히면 멈추고 보고하라.
