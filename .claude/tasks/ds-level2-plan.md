# Plan 지침 — 데이터 사이언스 레벨2 학습앱 (ds-level2)

## 너의 역할

이 프로젝트의 **Plan 단계** 담당이다. "데이터 사이언스 레벨2" 시험 대비 학습 웹앱의 설계 문서를 작성한다.

**구현하지 않는다.** 코드를 한 줄도 쓰지 마라. 오직 설계 문서 한 개만 만든다.
(데이터 스키마를 보여주는 짧은 JSON/JS 예시 1~2개는 허용한다. 문제 콘텐츠 자체는 쓰지 마라.)

## 수정 허용 범위

**오직 이 파일 하나만 생성한다.**

```
/home/user/my-blog/apps/ds-level2/spec.md
```

다른 어떤 파일도 만들거나 고치지 마라. 블로그의 기존 파일(`index.html`, `css/`, `js/`, `posts/`, `apps/2048/`)은 읽어도 되지만 절대 수정하지 마라.

## 프로젝트 배경

`/home/user/my-blog`는 마크다운 블로그 + 미니 웹앱 포트폴리오다. 만든 웹앱은 나중에 블로그 메인 페이지에 카드로 임베드된다.

먼저 읽어라:
- `/home/user/my-blog/CLAUDE.md` — 프로젝트 규칙
- `/home/user/my-blog/apps/2048/spec.md` — 앞선 앱의 설계 문서. **문서의 깊이와 형식은 이 수준을 따르되, 이번 앱은 규모가 훨씬 크므로 더 길어도 된다.**
- `/home/user/my-blog/css/tokens.css` — 블로그 디자인 토큰(색·폰트·간격). 앱은 자체 CSS를 갖되 톤을 맞춘다.

지켜야 할 규칙:
- 웹앱은 `/apps/ds-level2/` 폴더 안에 **자체 완결**된다. 바깥 파일에 의존하지 않는다.
- 프레임워크·번들러·빌드 없음. 순수 HTML, CSS, JavaScript. 브라우저가 파일을 그대로 읽는다.
- 외부 라이브러리는 최소화. CDN은 웹앱에서는 허용되지만 **의존성 0을 목표**로 하라. 코드 하이라이팅도 직접 만든 단순 토크나이저나 `<pre><code>` 단순 표시로 충분한지 판단하라.
- **모바일에서도 사용할 수 있어야 한다.** (출퇴근길 스마트폰으로 필기 문제 풀이가 주요 시나리오다.)
- `file://`로 열어도 동작해야 한다 → `fetch()`로 JSON을 읽지 말고, 데이터는 **클래식 `<script>`로 로드되는 JS 파일**에 담아 전역 레지스트리에 등록하는 방식을 검토하라. (2048 spec의 "왜 클래식 스크립트인가" 참고)
- 블로그 다크 모드와 같은 방식(`html[data-theme]` + `prefers-color-scheme`)을 따를지 판단하라.

## 사용자(학습자) 정보

- 웹 개발과 Python을 "직접 만들면서 배우는" 중급 학습자. 삼성전자 재직, 사내 JupyterLab과 개인 데스크톱의 Jupyter Notebook을 쓴다.
- 목표: **"데이터 사이언스 레벨2" 시험 합격.** 시험은 필기(개념·용어·코드 읽기)와 실습(Jupyter에서 데이터를 처리해 답을 구함)으로 구성된다고 가정한다.
- 사용자 요구사항 원문:
  1. 필기와 실습 둘 다 커버
  2. 실습은 **개인 데스크톱에 설치된 Jupyter Notebook**을 활용 (앱 안에서 Python을 실행하지 않는다 — Pyodide 같은 것 쓰지 마라)
  3. **필기 문제를 잔뜩** — 답과 정확하고 이해하기 쉬운 해설 포함
  4. 시험 문제를 이해할 수 있도록 **전문용어(영문 병기) 언급을 빼먹지 말 것**
  5. **색인 전체를 머리에 넣을 수 있게 점진적 학습**이 가능할 것

## 학습 색인 (이 구조를 앱의 커리큘럼 트리로 그대로 반영하라)

```
파트 A. 전처리
  1. SQL 학습
     1-1 SQL 기초
     1-2 SQL 중급
     1-3 SQL 고급
     1-4 SQL ↔ Pandas
  2. Pandas 학습
     2-1 Pandas 기초
     2-2 Pandas 데이터 정제
     2-3 Pandas 변환과 집계
     2-4 Pandas 병합과 결합
     2-5 Pandas 시계열
     2-6 Pandas 고급
  3. 라이브러리별 기본 사용법
     3-1 Python Native 문법
     3-2 Pandas 문법 기본
     3-3 Pandas 문법 심화
     3-4 Scikit-Learn
     3-5 statsmodels
     3-6 Scipy
     3-7 특수 라이브러리 및 수동 구현
  4. 복합 사용법
     4-1 다중 컬럼 및 전처리
     4-2 모델 평가 및 변수 선택
     4-3 파라미터 튜닝 및 군집화
     4-4 통계 검정 및 특수 모델링

파트 B. 운영자의 비법 모음
  1. Python native 문법 익히기        + 1-2 이해도 점검 문제
  2. pandas 문법 익히기               + 2-2 이해도 점검 문제
  3. 복합 패턴 — Python + pandas 조합의 원리 + 3-2 이해도 점검 문제
  4. 신뢰구간과 선형회귀분석          + 4-2 이해도 점검 문제
  5. 가설검정                          + 5-2 이해도 점검 문제
```

파트 B의 "N-2 이해도 점검 문제"는 색인상 별도 항목이다. 앱에서 이를 (a) 해당 강의 토픽의 퀴즈로 흡수할지, (b) 색인 그대로 별도 노드로 둘지 판단하라. "색인 전체를 머리에 넣는다"는 목표를 고려하면 **트리 표시는 색인과 1:1로 같아야** 사용자가 색인 자체를 암기하는 데 도움이 된다.

## 설계 문서에 반드시 담을 것

1. **앱 개요 한 문단** — 무엇을 만드는지.

2. **파일 구조** — `/apps/ds-level2/` 안의 파일과 역할. 특히 **콘텐츠(문제·해설·실습)와 엔진(UI·채점·진도)을 분리**하라. 콘텐츠는 토픽별 또는 챕터별 JS 데이터 파일로 나눠, **여러 Build 서브에이전트가 서로 다른 파일을 병렬로 작성해도 충돌하지 않게** 설계하라. 파일 수와 분할 단위(챕터 단위 권장)를 정하고 이유를 적어라.

3. **콘텐츠 데이터 스키마** — 다음 세 종류의 스키마를 확정하라. 필드 이름, 타입, 필수 여부, 예시 1개씩.
   - **토픽 요약 카드(cheat sheet)**: 핵심 개념, 반드시 알아야 할 전문용어(한글 + 영문 + 한 줄 정의), 핵심 코드 패턴 3~7개.
   - **필기 문제**: 유형(객관식 4지선다 / OX / 빈칸(단답) / 코드 출력 예측 / 코드 오류 찾기 등 — 시험 대비에 효과적인 유형을 골라 확정), 난이도(1~3), 문제문, 코드 블록(선택), 보기, 정답, **해설**(왜 정답인지 + 오답 보기가 왜 틀렸는지 + 관련 전문용어), 용어 태그(용어사전 연결용), 색인 노드 ID.
   - **실습 과제(Jupyter용)**: 과제 설명, **데이터 준비 셀**(인터넷 없이 재현 가능해야 한다 — `numpy` 고정 시드로 합성 데이터 생성 또는 `sklearn.datasets` 내장 데이터. 외부 CSV 다운로드 금지), 힌트, **정답 값**(숫자/문자열 — 앱이 채점할 수 있도록 결정적(deterministic)이어야 한다, 반올림 자릿수 명시), 모범 답안 코드(접기), 해설. 실습 과제는 실제 시험처럼 "값을 구해 입력하라" 형태를 기본으로 하라.
   - 문제 본문·해설에서 인라인 코드, 굵게, 코드 블록 정도를 표현할 최소 마크업 규칙을 정하라(풀 마크다운 파서 금지. 정규식 수준의 미니 포매터로 처리 가능한 범위).

4. **분량 목표** — 토픽당 필기 문제 수, 실습 과제 수, 전체 합계를 표로 제시하라. 기준: **필기 문제는 토픽당 12~15개(전체 350개 내외), 실습 과제는 토픽당 2~3개(전체 60개 내외)**. 파트 B의 점검 문제 노드는 문제 수를 더 늘려도 좋다. 이 표는 이후 Build 콘텐츠 에이전트에게 할당량으로 쓰인다. 챕터별 난이도 분포(1:2:3 비율)도 정하라.

5. **점진적 학습 설계** — "색인 전체를 머리에 넣는다"를 어떻게 달성할지.
   - 커리큘럼 트리 화면(색인과 1:1)과 노드별 상태(미학습 / 학습중 / 완료). 완료 기준(예: 퀴즈 정답률 80% 이상)을 정하라.
   - 학습 흐름: 요약 카드 → 필기 퀴즈 → 실습 → 다음 토픽. 잠금(unlock) 방식을 쓸지, 권장 순서만 표시할지 판단하라.
   - **오답 노트**: 틀린 문제를 모아 다시 풀기.
   - **복습 스케줄**: 라이트너(Leitner) 상자 같은 간단한 간격 반복(spaced repetition)을 넣을지 판단하라. 넣는다면 규칙을 구체적으로.
   - **모의고사 모드**: 여러 토픽에서 무작위 N문제, 제한 시간, 결과 리포트(토픽별 정답률로 약점 노출).
   - **용어 사전(glossary)**: 해설 속 전문용어를 탭하면 정의가 뜨는 방식. 용어 데이터를 어느 파일에 둘지, 콘텐츠 에이전트들이 병렬로 용어를 추가할 때 중복을 어떻게 병합할지.
   - 진도·오답·상자 상태는 `localStorage`에 저장. 저장이 막힌 환경에서도 앱이 동작해야 한다. 데이터 스키마와 키 이름, 버전 필드(추후 마이그레이션 대비)를 정하라. **진도 내보내기/가져오기(JSON)** 를 넣을지 판단하라 (회사 PC ↔ 집 PC ↔ 폰 사이 이동이 있다).

6. **실습 ↔ Jupyter 연동 방식** — 앱 안에서 코드를 실행하지 않는다. 다음을 설계하라.
   - 각 실습 과제의 셀을 **복사 버튼**으로 클립보드에 복사.
   - **`.ipynb` 파일 다운로드**: 토픽(또는 챕터) 단위로 실습 과제들을 하나의 노트북으로 묶어 브라우저에서 생성(Blob)해 내려받기. `.ipynb`의 JSON 구조(nbformat 4, cells, metadata)를 문서에 명시하라. 정적 `.ipynb` 파일을 저장소에 따로 두지 말고 **문제 데이터에서 생성**해 원본을 하나로 유지하라.
   - 사용자가 Jupyter에서 구한 값을 앱에 입력하면 채점(허용 오차 규칙 명시: 예를 들어 소수는 명시된 자릿수로 반올림해 비교).

7. **화면 구성** — 화면 목록(홈/대시보드, 커리큘럼 트리, 토픽 학습(요약·퀴즈·실습 탭), 오답 노트, 모의고사, 용어 사전, 설정)과 각 화면의 와이어프레임을 텍스트로. 단일 페이지(해시 라우팅 `#/topic/a-2-3` 등)로 갈지 다중 HTML로 갈지 판단하라. **모바일 우선** 레이아웃, iframe 임베드 시(블로그 카드 안에서 작은 크기) 어떻게 보일지.

8. **접근성·UX 세부** — 키보드로 보기 선택(1~4 숫자키), 정답 공개 전/후 상태, 해설의 용어 링크, 코드 블록 가로 스크롤, 긴 해설 접기, 다크 모드.

9. **Build 단계 작업 분할 계획** — Build를 몇 개의 서브에이전트로 나눌지 제안하라. 권장: 엔진 1개 + 콘텐츠 N개(챕터 단위). 각 콘텐츠 에이전트가 받을 파일과 분량, 엔진과 콘텐츠가 동시에 진행되도록 **스키마를 먼저 고정**해야 하는 이유. 콘텐츠 에이전트가 실습 과제의 정답 값을 **반드시 Python으로 실제 실행해 검증**해야 한다는 규칙을 포함하라(이 컨테이너에 pandas/numpy/sklearn/scipy/statsmodels 설치를 시도 중이다. 설치가 안 되면 대안도 적어라).

10. **검증 항목(Review 체크리스트)** — 엔진: 라우팅, 채점, 진도 저장/복원, 오답 노트, 모의고사, ipynb 다운로드가 실제 Jupyter에서 열리는지(nbformat 유효성), 모바일 뷰포트, 다크 모드, localStorage 차단 시 동작. 콘텐츠: 정답 오류 검출 방법(스키마 검증 스크립트 — 정답 인덱스 범위, 중복 ID, 빈 해설, 용어 태그가 사전에 존재하는지), 실습 정답 재실행 검증, 표본 문제의 해설 품질 기준.

## 판단해서 정할 것 (이유와 함께 문서에 적어라)

- 문제 유형 세트를 무엇으로 확정할지 (객관식만으로 갈지, 단답·코드출력 등을 섞을지)
- 노드 잠금(unlock) 방식 vs 자유 탐색 + 권장 순서
- 간격 반복(Leitner)을 넣을지
- 코드 하이라이팅을 넣을지(자체 미니 토크나이저 vs 없음 vs CDN)
- 색인 파트 B의 "이해도 점검 문제" 노드 처리 방식
- 다크 모드를 블로그와 연동할지
- 진도 내보내기/가져오기 포함 여부

## 문서 형식

한국어로 작성한다. 전문용어는 영문을 병기한다. 구현자가 이 문서만 읽고 바로 만들 수 있을 만큼 구체적이어야 한다. 데이터 스키마는 예시 JSON/JS로 보여주되, 실제 문제 콘텐츠는 만들지 마라. UI 코드는 쓰지 마라 — 구조와 동작을 말로 설명하라.

문서 맨 위에 한 문단으로 "무엇을 만드는지"를 요약하라.
