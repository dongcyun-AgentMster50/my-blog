# Plan 지침 — 2048 게임

## 너의 역할

이 프로젝트의 **Plan 단계** 담당이다. 2048 게임 웹앱의 설계 문서를 작성한다.

**구현하지 않는다.** 코드를 한 줄도 쓰지 마라. 오직 설계 문서 한 개만 만든다.

## 수정 허용 범위

**오직 이 파일 하나만 생성한다.**

```
D:\01_claude_my-blog\apps\2048\spec.md
```

다른 어떤 파일도 만들거나 고치지 마라. 블로그의 기존 파일(`index.html`, `css/`, `js/`, `posts/`)은 읽는 것은 되지만 절대 수정하지 마라.

## 프로젝트 배경

`D:\01_claude_my-blog`는 마크다운 블로그 + 미니 웹앱 포트폴리오다. 만든 웹앱은 나중에 블로그 메인 페이지에 카드로 임베드된다.

프로젝트 규칙(`CLAUDE.md`)을 먼저 읽어라. 특히 지켜야 할 것:

- 웹앱은 `/apps/{앱이름}/` 폴더 안에 **자체 완결**된다. 바깥 파일에 의존하지 않는다.
- 프레임워크·번들러 없이 순수 HTML, CSS, JavaScript.
- 외부 라이브러리는 최소화. 웹앱에서는 CDN을 써도 되지만, 2048은 라이브러리 없이 충분히 만들 수 있으니 **의존성 0을 목표로 하라.**
- **모바일에서도 사용할 수 있어야 한다.**
- 빌드 단계가 없다. 브라우저가 파일을 그대로 읽어 동작해야 한다.

## 만들 것

방향키로 숫자 타일을 밀어 합치는 2048 퍼즐 게임. 사용자가 요청한 것:

- 방향키로 타일 이동
- 같은 숫자끼리 합쳐짐
- **점수판**

## 설계 문서에 반드시 담을 것

1. **파일 구조** — `/apps/2048/` 안에 어떤 파일을 둘지와 각 파일의 역할. 파일을 나눌지 하나로 합칠지 판단하고 이유를 적어라.

2. **게임 규칙 정의** — 4×4 격자, 새 타일 생성 규칙(2와 4의 비율), 한 번의 이동에서 타일이 합쳐지는 규칙(한 이동에 같은 타일이 두 번 합쳐지지 않는다는 점 포함), 승리·패배 판정 조건.

3. **핵심 알고리즘** — 한 방향으로 미는 연산을 어떻게 구현할지. 네 방향을 각각 짜지 않고 하나의 연산으로 처리하는 방법을 검토하라(예: 격자 회전 또는 전치 후 한 방향만 처리).

4. **입력 처리** — 데스크톱은 방향키. **모바일은 반드시 스와이프를 지원해야 한다** — 휴대폰에는 방향키가 없다. 터치 이벤트를 어떻게 방향으로 변환할지 적어라. 스와이프로 페이지가 스크롤되는 문제도 어떻게 막을지 다뤄라.

5. **점수 처리** — 점수 계산 방식(합쳐진 타일 값의 합), 최고 점수를 `localStorage`에 저장할지, 저장한다면 저장이 막힌 환경에서도 게임이 동작하도록 하는 방법.

6. **화면 구성과 스타일** — 격자·타일·점수판의 배치. 타일 숫자별 색상 규칙. 블로그에 iframe으로 임베드될 것을 감안한 크기 정책(고정 픽셀이 아니라 컨테이너에 맞춰 늘어나야 한다).

7. **접근성과 상태 표시** — 게임 오버·승리 시 무엇을 보여줄지, 다시 시작 버튼, 키보드 포커스 처리.

8. **검증 항목** — 다음 Review 단계에서 무엇을 확인해야 하는지 체크리스트로 정리하라. 특히 "한 이동에 같은 타일이 두 번 합쳐지지 않는가" 같은 규칙 버그를 어떻게 확인할지 포함하라.

## 판단해서 정할 것

다음은 정답이 정해져 있지 않다. 네가 판단하고 **이유와 함께** 문서에 적어라.

- 애니메이션을 넣을지 (넣으면 구현이 복잡해진다. 가치가 있는가?)
- 실행 취소(undo) 기능을 넣을지
- 블로그의 다크 모드와 연동할지, 아니면 자체 색상만 쓸지
- 격자 크기를 4×4로 고정할지 선택 가능하게 할지

## 문서 형식

한국어로 작성한다. 구현자가 이 문서만 읽고 바로 만들 수 있을 만큼 구체적이어야 한다. 다만 코드를 통째로 쓰지는 마라 — 알고리즘은 말과 의사코드로 설명하고, 실제 코드는 Build 단계에 맡겨라.

문서 맨 위에 한 문단으로 "무엇을 만드는지"를 요약하라.
