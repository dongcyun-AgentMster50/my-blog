# Review 지침 — 성장 빙고

## 너의 역할

이 프로젝트의 **Review 단계** 담당이다. Build 담당이 만든 웹앱 "성장 빙고"를 **독립적으로** 검증하고 `review.md`를 쓴다. 너는 이 코드를 만들지 않았다. Build 담당의 보고를 믿지 말고 직접 확인하라.

## 먼저 읽을 것 (경로는 저장소 루트 기준)

1. `apps/growth-bingo/spec.md` — 승인된 설계 문서. 판정 기준이다. 특히 2절(규칙), 3-2절(49칸 표), 12절(`canClaim` 검사 순서), 14절(엣지 케이스), **15절(검증 항목 체크리스트)**.
2. `CLAUDE.md` — 프로젝트 규칙.
3. `apps/growth-bingo/` 아래의 구현 전체.

## 수정 허용 범위

- **반드시 만든다:** `apps/growth-bingo/review.md`
- **고쳐도 된다:** `apps/growth-bingo/` 안의 구현 파일(`index.html`, `style.css`, `print.html`, `print.css`, `js/*.js`, `tests/*.js`). 발견한 문제는 직접 고친다.
- **금지:** `spec.md` 수정, 블로그 본체(`index.html`, `post.html`, `css/`, `js/`, `posts/`, `vendor/`)와 다른 앱 폴더 수정, `.claude/`·`CLAUDE.md`·`.nojekyll` 수정, git 커밋·푸시.
- **판의 49칸 내용·네모 수·위치는 바꾸지 않는다.** 구현이 spec 표와 다르면 구현을 spec에 맞춘다.
- 임시 파일과 스크린샷은 `/tmp`에만 둔다. 셸에서 `rm -r`, `find -delete`, `sudo` 형태는 훅이 차단한다.

## 검증 방법

### 1. 테스트와 판 대조

- `node apps/growth-bingo/tests/balance.test.js`, `node apps/growth-bingo/tests/rules.test.js`를 돌린다.
- 테스트가 통과한다고 끝내지 마라. **테스트 자체가 spec 15절 A의 시나리오를 실제로 검사하는지** 읽어 확인한다(기대값을 구현에 맞춰 느슨하게 쓴 곳이 없는지).
- `js/board-data.js`의 49칸을 spec 3-2절 표와 **칸 하나하나** 대조한다: 위치, 영역, 종류, 네모 수, 제목, 기준 문구. 스크립트로 spec 표를 읽어 비교하는 것을 권한다.
- 균형 숫자를 네가 따로 짠 짧은 스크립트로 한 번 더 계산해 spec 3-4절과 맞는지 본다(16줄 영역 분포, 7줄 조합 11,440가지의 스티커 최소·중앙·최대).

### 2. 규칙 — 순수 함수를 직접 두드린다

`rules.js`를 Node에서 불러 spec 12절의 검사 순서와 14절의 엣지 케이스를 직접 시험한다. 최소한 다음을 포함한다.

- 하루 4개 상한, 영역 2개 상한, 같은 칸 하루 1개
- 레벨 건너뛰기 시도, 한 사다리 하루 한 계단, **확인 대기만으로는 다음 레벨이 열리지 않음**
- 주차 고정 칸의 기간 경계(10일차는 되고 11일차는 안 됨 등)
- 주 1회 칸이 "최근 7일"이 아니라 주차 기준으로 판정되는지
- 근력 하루 1개, 같은 부위 이틀 연속 금지, 달리기·트레일 이틀 연속 금지
- "어제 한 일" 기록이 간격 규칙을 우회하지 못하는지
- 쉬는 날 칸과 근력·유산소의 충돌
- 인정 기간이 지난 확인 대기의 처리
- 빙고 수 계산: 가로·세로·대각선, 확정 스티커만 반영

### 3. 브라우저 — 실제로 연다

Chromium과 Playwright가 설치되어 있다(`require('playwright')`, `chromium.launch()`에 옵션 불필요, 새로 설치하지 마라). 저장소 루트에서 `python3 -m http.server`로 띄우고 확인한다.

- 폭 360px(휴대폰)과 1280px에서 콘솔 오류·경고 없이 열리는지. 7×7 판이 **가로 스크롤 없이** 보이는지. 스크린샷을 찍어 직접 본다.
- 첫 실행 흐름 → 시작일·가족 비밀번호 설정.
- 칸 눌러 상세 → "했어요" → 확인 대기 → 가족 비밀번호로 도장 → 확정 → 새로고침 후 유지.
- 가족의 도장 취소.
- 하루 상한 도달 시 사유 문구.
- 길잡이: 추천 7줄 표시와 예상 완료일이 나오고, 스티커를 찍으면 갱신되는지. 계산이 눈에 띄게 느리지 않은지 시간을 잰다.
- 시작일을 과거로 바꿔 3주차·5주차 상태, 35일이 지난 상태를 본다.
- 한 줄을 실제로 완성해 빙고 수가 오르는지(디버그 수단이나 저장소 직접 조작으로 상태를 만든다).
- 내보내기 → 초기화 → 가져오기로 복구되는지. 초기화가 화면 안 확인 절차를 거치는지.
- `localStorage`가 막힌 환경(Playwright에서 접근 시 예외를 던지게 만들기)에서 앱이 죽지 않고 알림을 보이는지.
- `?embed=1` 축소 모드. 블로그 메인의 iframe 크기(대략 폭 320~700px)에서 쓸 만한지.
- `print.html`: 인쇄 미디어로 PDF를 만들어 A4 한 장에 판이 들어가는지, 둘째 장에 규칙이 있는지.
- 다크 모드, 키보드만으로 조작, 포커스 표시.
- `confirm`/`alert`/`prompt`를 쓰는 곳이 없는지 코드에서 검색한다.

### 4. 코드

- `board-data.js`, `rules.js`, `guide.js`가 DOM·`localStorage`·`Date.now()`·`Math.random()`을 쓰지 않는지.
- 규칙 코드에 칸 id가 박혀 있지 않은지.
- 가족 확인이 `family-gate.js` 경계 뒤에 있는지(이식성).
- 사용자·저장소에서 온 문자열을 `innerHTML`에 그대로 넣는 곳이 없는지(보상 문구, 가져온 JSON 등).
- 외부 리소스(CDN, 폰트) 요청이 없는지.
- 화면 문구에 개발 용어나 어색한 표현이 없는지.

## 문제를 발견하면

1. 직접 고친다(허용 범위 안에서).
2. 고친 뒤 **같은 방법으로 다시 확인**한다. 확인하지 않은 수정은 "고침"이라고 쓰지 마라.
3. 고칠 수 없거나 설계 판단이 필요한 것은 고치지 말고 `review.md`에 남긴다.

## `review.md`에 담을 것

한국어. 다음 순서로.

1. **결론** — 한 문단. 출시해도 되는가, 남은 문제는 무엇인가.
2. **검증한 것** — 체크리스트 형식. 항목마다 결과(통과 / 고침 / 실패 / 확인 못 함)와 **어떻게 확인했는지**(명령, 시나리오). 실제로 하지 않은 것은 "확인 못 함"으로 적는다.
3. **발견한 문제와 조치** — 심각도(높음·중간·낮음), 재현 방법, 원인, 고친 내용, 재확인 결과.
4. **남은 문제** — 고치지 않은 것과 이유.
5. **spec과 다른 점** — 구현이 설계와 다른 부분.
6. **실기기에서 사용자가 확인할 것** — 자동 검증으로 못 본 것.
