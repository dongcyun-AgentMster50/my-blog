# Build 지침 — MedReader 2a단계: PDF 특성 측정 도구 `dev/profile.mjs`

## 배경 — 왜 이걸 지금 만드는가

대상 PDF(`ILMA_2021_20th_ed_Harrison.pdf`, 729쪽)는 **임시본**이다. 며칠 내로 **7000쪽짜리 실제 자료**(같은 형식의 텍스트 PDF)로 교체되고, 작업은 그것을 기준으로 다시 진행된다.

그때 **추측이 아니라 측정으로 시작**해야 한다. 이 도구가 그 진입점이다.

이게 필요하다는 근거는 실측에서 나왔다. `[실측]` `figure-caption` 역할이 729쪽 전체에서 **단 한 번도 발동하지 않았다.** 코드는 `/^(FIGURE|FIG\.|TABLE)\s*\d/i`(숫자가 바로 오는 형식)를 보는데 이 책은 `TABLE II-9` 형식이다 — **해당 형식 362줄이 있는데 감지 0건**이고, 4-8의 캡션 가점 신호·완화 경로·region bbox 합치기가 **전부 죽은 코드**였다. 합성 픽스처는 코드의 정규식에 맞춰 만들어지므로 **단위 테스트 59개가 전부 통과하면서도** 이 결함은 보이지 않았다. **실물 통계로만 보인다.**

## 너의 역할

`apps/medreader/dev/profile.mjs` 를 만든다. **그것만 한다.**

- **출력물에 원서 문장을 넣지 마라.** 패턴·빈도·수치만. 예시 문자열이 꼭 필요하면 **40자 이하로 자르고** 그것도 `--samples` 플래그가 있을 때만.

## 구현 요구사항

### 실행 형태

```
node apps/medreader/dev/profile.mjs <pdf 경로> [옵션]
  --pages N      앞에서 N쪽만 (기본: 전체). 7000쪽 대비 표본 모드
  --stride N     N쪽마다 하나씩 (빠른 훑기)
  --json <path>  BOOK_PROFILE 초안을 JS 모듈로 출력
  --samples      진단용 짧은 예시 문자열 포함 (기본 off)
```

- **Node 전용.** `pdfjs-dist` 는 **legacy 빌드**를 써야 한다(`pdfjs-dist/legacy/build/pdf.mjs`) — 일반 빌드는 Node 에서 `DOMMatrix is not defined` 로 죽는다.
- `pdfjs-dist` 가 레포에 없으므로 **스크래치패드 설치본을 찾아 쓰거나**, 없으면 **명확한 안내 메시지**와 함께 종료하라(설치 명령을 알려주는 형태). 레포에 `node_modules` 를 만들지 마라.
  스크래치패드 설치본: `<스크래치패드>`
  경로를 하드코딩하지 말고 **환경변수(`MEDREADER_PDFJS`)나 인자로 받고**, 못 찾으면 안내하라.
- 진행 표시를 내라(7000쪽은 오래 걸린다). 중간에 `Ctrl+C` 해도 그때까지 집계를 출력하면 더 좋다.

### 측정 항목 — spec 2-4 표 전부

1. **기본**: 쪽 수, 쪽 크기 분포, 본문 폰트 중앙값(Fm), 행간 중앙값(Lm), 쪽당 아이템·줄 수 분포.
2. **거터**: run 간격 히스토그램의 중앙부 피크 → **거터 폭 실측값과 `RUN_GAP_FACTOR` 권장값**(거터 폭 / Fm 의 하한보다 작은 값). 2단/1단 쪽 비율.
3. **문항 번호 형식**: 줄·문단 머리에서 `\d+\.` / `[IVXLC]+-\d+\.` / `[A-Z]+-\d+\.` / `Q\d+` / `문제\s*\d+` 등 **후보별 빈도**. 최빈 형식과 **번호 자릿수 최대값**.
4. **보기 글자 범위**: 줄 머리 `[A-Za-z]\.` 의 글자별 빈도 → **실제로 쓰이는 최대 글자**(이 책은 F 까지 있다).
5. **정답 문구**: 문항 번호 뒤에 오는 상용구 n-gram 빈도 상위 N(예: `the answer is`). 언어가 영어가 아닐 수 있다.
6. **캡션**: `FIGURE|FIG|TABLE|표|그림|図` 등으로 시작하는 줄을 모아 **접두어별 빈도 + 바로 뒤 토큰의 형태**(`\d` / `[IVXLC]+-\d` / 기타). **이 항목이 이 도구를 만드는 직접적 이유다** — 코드의 현재 정규식으로 몇 건이 잡히는지도 함께 출력해 **죽은 코드를 드러내라.**
7. **머리말·꼬리말**: 상단·하단 영역 줄을 숫자→`#` 정규화해 빈도 집계 → 반복 문자열 상위 N. **쪽번호 자릿수 최대값**.
8. **품질 지표**: `[a-z][A-Z]` 붙음 후보, 20자 이상 낱말, 텍스트 0인 쪽, 회전 줄 수.
9. **컬럼 탐지 실패 후보**: **run 2개의 x 간격이 페이지 폭 1/3 초과인 줄 수**(쪽 목록 포함). 거터 탐지가 실패하면 이 수가 튄다.
10. **용량·성능**: `buildPageLayout` 평균 ms/쪽, 저장본(아이템 제거 후) 바이트 추정 → **전체 예상 `pages` 용량**. spec 9-2 목표는 쪽당 5~10KB다.

### 출력

- **사람이 읽는 요약**을 표 형태로 stdout 에.
- `--json` 이면 **`BOOK_PROFILE` 초안을 JS 모듈로** 쓴다(spec 2-4 의 필드 구조 그대로, 주석에 측정 근거 수치 포함). 값을 못 정하면 `null` 과 `// TODO: 측정값 불충분` 주석을 남겨라 — **틀린 값을 자신 있게 쓰는 것보다 낫다.**
- **경고 섹션**: 코드의 현재 상수·정규식과 측정값이 어긋나는 항목을 모아 **"이 책에서는 X가 죽은 코드"** 식으로 명시하라.

### 설계 제약

- 집계 로직은 **순수 함수로 분리**해 테스트 가능하게 하라(`profile-lib.mjs`). I/O·pdf.js 접근과 섞지 마라.
- `js/text/*` 를 **재구현하지 마라.** `buildPageLayout` 등을 import 해서 쓰라. 단 **수정은 금지**다.
- 7000쪽에서 **메모리가 터지지 않게** 하라 — 페이지 결과를 전부 배열에 쌓지 말고 누적 집계하라. `page.cleanup()` 을 반드시 호출하라.
